# AGENTS.md — edamame

Guidance for human and agentic contributors working in this repository. `CLAUDE.md` is a symlink to this file; edit one, update both.

## Project Overview

`edamame` is a Rust TUI application for viewing and editing Markdown files in the terminal: `ratatui` for rendering, `pulldown-cmark` for parsing, `ropey` for rope-based text editing. The crate ships as both a binary (`edamame`) and a library (so integration tests can import it).

> **Security:** edamame opens untrusted documents, so any change to a content-handling path (image/SVG decode, remote fetch, Mermaid, link opening, HTML export, subprocess spawning) must preserve the hardening in [`docs/security.md`](docs/security.md). Read it — and the checklist in [`docs/dev/security-invariants.md`](docs/dev/security-invariants.md) — before touching those areas.


`.githooks/pre-push` refuses to push a commit whose message carries an AI co-author trailer (`Co-Authored-By: Claude …`, `Claude-Session:`, `noreply@anthropic.com`). ## Test Commands

```bash
cargo test --no-fail-fast               # all unit + integration tests
cargo test -- --list                    # list all test names
cargo test -- document::buffer::tests::insert_char --exact   # one test by exact name
cargo test parse_heading                # by name substring
cargo test --lib                        # unit tests only (covers every module,
                                        #   incl. `app`; main.rs declares none)
cargo test --test renderer              # one integration file (ui, editing,
                                        #   source_map, palette, diagrams, …)
cargo insta review                      # review / accept updated snapshots
```

**Use `--no-fail-fast`, and expect the file-watcher tests to fail under an agent sandbox.** Plain `cargo test` stops at the first failing *target*, so a lib-target failure aborts the run before `tests/` is built — every integration test silently goes unrun while the summary still looks real. `watcher::file_watcher` and `tests/watcher.rs` need live filesystem-change notifications (FSEvents / inotify), which a sandbox typically withholds, so four tests there time out (`expected a debounced change: Timeout`). Disregard *only* watcher timeouts; treat any other failure as real. `cargo nextest run` also runs every target regardless of failures and is faster where installed.

**Test frameworks:** `insta` (snapshots), `proptest` (`tests/source_map.rs`), `tempfile`, `ratatui::backend::TestBackend` (headless widget rendering).

**Environment-touching tests take `crate::test_env::env_lock()` — readers included — and mutate only through `test_env::EnvGuard`.** `std::env::set_var` is `unsafe` because it races any concurrent `env::var`, and cargo runs a binary's tests on parallel threads, so the exclusion must be *crate-wide*: `config::config` writes `XDG_CONFIG_HOME` while `cli::doctor` reads it; `terminal::capabilities` writes `TERM_PROGRAM` while `cli::doctor` reads that. A per-module lock cannot exclude either pair. `EnvGuard` restores on drop so a failing assertion can't leak a variable pointing at a deleted tempdir. **`config::persistence::SuppressGuard` is serialized by that same lock** and takes none of its own — hold `env_lock` for the whole test body, not just across the guard: these tests are shaped "assert nothing was written, drop the guard, assert the same call *does* write", and a separate mutex released with the guard would let another test's suppression straddle that second half.

**A test that can reach `Config::save` takes `crate::test_env::config_isolation()`.** Nothing redirects `~/.config/edamame` during a test run, so an unguarded save rewrites *the developer's own config file* — and the asserted values are exactly the damaging ones (an update-check test recording `update_notified_for = "v999.0.0"` silences the real update notice permanently). The helper bundles `env_lock` with a `persistence::SuppressGuard` so `Config::save` returns `Ok(())` without writing. Hold it for the whole test body and take it only once — it is the crate-wide mutex. The one test needing a *real* write (`save_writes_nothing_while_config_writes_are_suppressed`) takes `env_lock` plus an `EnvGuard` pointing `XDG_CONFIG_HOME` at a tempdir. The check: `cargo test` creates no file under the config directory.

**Do not** write tests for live terminal capability probing (`Picker::from_query_stdio`), cross-platform clipboard (OS clipboard paths race between parallel tests), or the crossterm mouse wire protocol — all covered by manual smoke testing. *Do* test mouse logic at the `MouseDispatcher` + `mouse_ops::apply` layer: both are pure functions of an input event and an editor state.

### Built-in themes

`BUILTIN_THEMES` in `src/config/theme.rs` lists every compiled-in theme (Edamame, Dracula, Nord, Gruvbox, Catppuccin, …); each constructor lives in its own file under `src/config/themes/`. `Config::ensure_default_files` creates `themes/` empty — built-in theme files are never written to disk, and `read_theme_named` short-circuits to `Palette::builtin(name)` before any disk read, so a user file with a built-in name is ignored. To add a built-in: write `src/config/themes/<name>.rs` with a `pub fn theme()` and add it to `BUILTIN_THEMES`; the load path and the theme-picker / settings cycle (via `list_theme_names`) pick it up automatically. Custom user themes go in `~/.config/edamame/themes/<name>.toml` under any name not in the registry.

**Indexed-color substitution.** `256 Dark` / `256 Light` are the only built-ins authored against the xterm-256 cube; every other theme picks 24-bit colors that an indexed terminal quantizes, routinely landing fg and bg on the same entry. So without truecolor, `app::theme_fallback::apply` swaps `config.theme` for the matching indexed built-in (dark/light follows the *current theme's* appearance, not just the `appearance` key) and `ThemeDowngradeModal` reports it.

- **Exempt themes** are `theme::INDEXED_SAFE_THEMES`, for which `indexed_fallback_theme` returns `None`: the two `256 *` targets (which also makes the swap idempotent across reloads) plus `Monochrome Dark`, whose every palette slot is `Color::Reset`. The exemption covers the warning as much as the swap; `indexed_safe_themes_are_registered` pins the list against `BUILTIN_THEMES`.
- **One terminal change, one modal.** `ThemeDowngradeModal` carries the news except when the capabilities notice fires on the same launch, where the notice absorbs the prose via `with_theme_downgrade`. Both render `ui::cap_summary::theme_downgrade_lines`, and both hand `ModalView` *paragraphs*, not pre-broken lines.
- **Three invariants.** (1) The swap happens **before the first frame** in `App::new` — a modal explaining unreadable colors that is itself unreadable is worse than useless. (2) It is **never persisted**: the user's choice is stashed in `Config::theme_downgraded_from` and written back in `theme`'s place by `Config::save`, because one `config.toml` is typically shared with a truecolor machine. (3) Both paths resolving a theme from a freshly-read `Config` must call `theme_fallback::apply` — startup *and* the external-editor reload.
- **`NoColor` is exempt at the *depth* end**: `App::new` passes `monochrome` to `Theme::from_file`, which strips every color whatever the theme, so a swap there would be invisible. Below 24-bit color `App::media_renderable` also refuses images and diagrams outright — same quantization argument, likewise session-only, so a persisted `Always` survives for the user's capable terminal. **Enforced at the write sites:** `WelcomeModal::save_outcome` writes the three media fields only when `image_capable`, so the `Never` the modal *displays* below truecolor is never persisted. And when the notice carries the downgrade it drops its "Adjust settings" button — with theme, images and diagrams all disabled, the welcome modal has nothing left but the vim toggle.
- **While the stash is set, `config.theme` is effectively unwritable** (`Config::save` puts `theme_downgraded_from` in its place), so every path committing a theme *choice* must go through `Config::set_theme`, which clears it: the theme picker's selection and the export-theme modal's new theme. A bare `app.config.theme = …` paints the screen but silently drops the choice at save time. The only legitimate direct assignments are `theme_fallback::apply` itself and the picker's transient preview / revert, which deliberately do *not* clear the stash — `Esc` must restore the substitution.

### Architectural layers

Higher layers depend only on lower ones:

0. `cli` — argument parsing and the print-and-exit flags (`--help` / `--version` / `--doctor`); never starts the TUI
1. `main` — CLI dispatch, config load, terminal lifecycle
2. `app` — event loop, modal stack, autosave, external-editor flow
3. `ui` — ratatui widgets; `EditorView` dispatches to `PreviewView` / `RenderedView` / `RawView`; modal overlays composite on top
4. `input` — `ModeHandler` trait + `DefaultHandler`; `MouseDispatcher`
5. `editor` — `EditorState`; owns `Buffer`, `Cursor`, `History`, `Mode`, `ParsedDoc`
6. `document` — `Buffer`, `Cursor`, `History`, `ParsedDoc`, `Selection`, `SourceMap`, grapheme helpers
7. `markdown` — parser → AST → renderer; `parse_offsets` and `inline_col_map` feed `SourceMap`
8. `config` — `Config`, `KeyMap`, `Theme` (loaded once at startup)
9. `image`, `diagram`, `export`, `docs` — leaf subsystems used by the renderer / app
10. `terminal` — raw terminal setup / teardown / capability probing

`docs` is the one leaf reached from *above* layer 3: `Action::OpenDoc` carries a `docs::DocId`, `config`'s first and only dependency on another top-level module. Legal because `docs` is a true leaf — static strings and slug metadata, parsing nothing, importing nothing from this crate — but worth knowing before adding a second edge into `config`.

## Module Facade Pattern

Every top-level module has both a file (`src/config.rs`) and a subdirectory (`src/config/`). The file declares submodules with `pub mod` and re-exports public types with `pub use`, keeping call-site imports clean:

```rust
use crate::config::{Config, KeyMap, Theme};   // not crate::config::config::Config
```

Always follow this pattern for new top-level modules. Several mid-level modules (`editor::mouse_ops`, `editor::list_edit`, `markdown::parser`, `markdown::renderer`, `config::themes`, `config::theme_file`, `ui::rendered_view`, `app::modal`) follow it recursively.

## Architectural Notes

These decisions are easy to break if you don't know they exist.

### Command-line entry points

- **`main` is a dispatcher over `cli::Invocation`, and the parser is hand-rolled on purpose.** `clap` is deliberately absent from the graph (hence `mermaid-rs-renderer` declared `default-features = false` — its `cli` feature would drag clap in), so a new flag is a match arm in `cli::args`, not a new dependency. Arguments are taken as `OsString`: `std::env::args()` *panics* on a non-UTF-8 argument, which is a legal Linux file name, so flags are matched only after a successful `to_str()` and anything else falls through to the positional arm intact.
- **`--doctor` never re-derives capability text.** The five capability rows come from `ui::cap_summary::CapSummary::from_caps`, the same builder the welcome modal and capabilities notice use; a second phrasing would drift. `cli::doctor` adds only the *system* half (OS, terminal, `TERM`, `COLORTERM`, locale, tmux) and the `Status::Unknown` state. Every row describes the *machine*, never the person — the report is written to be pasted into a public issue tracker, which is why the config directory is absent (a username in the common case, carrying only "this path is or isn't the default"). A new row owes the same test.
- **That third state exists because the probe needs a tty.** `Capabilities::detect` writes escape sequences and reads replies off the terminal, so `edamame --doctor > report.txt` would pollute the file and report "no image support" for a terminal that has it. `doctor::run` checks `IsTerminal` on stdout *and* stdin, falls back to `Capabilities::env_only`, and marks exactly the two probe-derived rows — Images and Keyboard — unknown.
- **System facts are file reads, never subprocesses.** `/etc/os-release` on Linux, `SystemVersion.plist` on macOS (a string scan), `$TERM_PROGRAM_VERSION` for the terminal version; Windows reports the bare OS name. Spawning `sw_vers` / `lsb_release` would add a process spawn to an area `docs/security.md` hardens; every lookup degrades to a coarser answer instead of an error.
- **`--no-config` is enforced at every read and write site, through one gate.** Skipping the load is the easy half; the trap is a mid-session *write* overwriting the user's real config with compiled defaults. `config::persistence` owns one process-global `AtomicBool` that `main` clears via `disable_config_dir()` before any config file is touched, exposed as `config_writes_allowed()` and `config_reads_allowed()` — two names for one fact, so a reader isn't guarded by a function with "writes" in its name.
  - **Four write sites, all four ask:** `Config::save` (returns `Ok(())` without writing — nothing went wrong); the keybinds overlay's `try_persist` (whose `save_to` *truncates* `keybindings.toml` from in-memory overrides a `--no-config` session never read, so one rebind would wipe the real file); the export-theme modal (refused outright — a custom theme *is* its file, so a suppressed write would leave `set_theme` naming an unresolvable theme); and `App::open_config_in_editor` (refused: it both seeds `config.toml` and reloads from it). `ensure_default_files` is the sole exception, and only because `main` never calls it under the flag.
  - **The read half needs the same treatment**, because the config dir is read again mid-session by surfaces enumerating what the user dropped in. Ungated, `--no-config` would still list — and on selection load — `themes/*.toml` in the theme picker, the settings overlay's theme cycle, and the export-theme source list. Three sites ask `config_reads_allowed()`: `theme::list_theme_names` (which all three theme surfaces build from), `readers::list_export_stylesheets`, and `readers::read_theme_named` as defense in depth — it substitutes the capability-appropriate built-in and returns `None` for the fallback name, since there is no rename to persist and nothing is *missing* (a `MissingTheme` modal every launch would be noise). A new reader or writer owes the matching check.
  - **The gate is a global because a `Config` field was not enough.** It was a `#[serde(skip)]` `persist` field once; `App::open_config_in_editor` reloads config from disk and assigns wholesale, so the flag silently reverted to its serde default mid-session. A per-process fact belongs in a per-process place, and there is deliberately no way to re-enable it. Messages reporting a settings change append `config::unpersisted_suffix()` (`NOT_PERSISTED_NOTE`, one const so all three flashes phrase it identically) so "Configuration updated" never claims a write that didn't happen.

### Hybrid editing model

- **Virtual blocks for blank lines.** `ParsedDoc::build` synthesises a one-byte block for every blank line, so the cursor lands on each as its own block and the blank survives in `RenderedView` when the surrounding block goes raw. Don't use `parse_offsets::covering_ranges` for cursor mapping — it absorbs blank-line bytes into adjacent blocks.
- **`per_block_own` vs. extended ranges.** `ParsedDoc` tracks per-block *own* rendered line counts (for `RenderedView`'s raw-replacement region) *and* extended covering ranges (for cursor lookup). Mixing them collapses gap blank lines when the cursor enters the previous block.
- **Loose lists stay one block; blanks are annotated, not split.** One `Block::List`, with blank source lines per item recorded in `ListItem::blank_lines_before` (`parser::post_pass::annotate_list_blanks`); the renderer emits that many blank `Line`s before the item, so spacing is kept while numbering comes from pulldown-cmark. Don't reintroduce `split_lists_on_blank_lines` — fragmenting forced per-group `start` re-derivation and block/range surgery for no rendering benefit.
- **The reveal depends on rendered rows staying 1:1 with source lines.** `RenderedView` maps rendered rows to source lines via `block_text.split('\n')`, so every separator blank must emit exactly one row. `editor::state::sub_lines_in_block` — the single raw→rendered line mapping — counts *separator* blanks (a blank run ending at a top-level marker) as rows while skipping interior-item blanks and soft-break continuations; "count only non-blank lines" reveals the cursor line one row too high. It answers a whole block per call (`cursor_sub_line_in_block` indexes the result) because per-line queries were quadratic.
  - **Four callers must agree and must never re-derive it:** `RenderedView`, `cursor_rendered_line_idx`, `mouse_ops::coord`'s `revealed_cursor_line` (through the latter), and `editor::state_source_lines` (the gutter). Drift maps a click on a revealed line against *rendered* spans, so a line whose markers were dropped places the cursor short by the marker width.
  - `state_source_lines` *inverts* the function rather than hand-writing an inverse. Three rules: **last writer wins** (a line rendering no row shares its sub-row with the next line, whose text is on screen); skip blocks with `block_own_line_count == 0`; and read the document from `ParsedDoc::source`, not the live `Buffer` — it resolves parse-time byte ranges, and the table is memoised per parse.
  - **Its inputs are shared too:** `rendered_view::raw_text::raw_block_cursor` is the single derivation of the `(block source, raw line index, column)` triple both callers feed it. `RenderedView` keeps one branch of its own, for a stale parse, rebuilding the triple from `cursor_block_line_range` so just-typed characters show before the reparse.
- **Jitter-suppression reveal.** `cursor_block_revealed()` returns false during a 120 ms `RAW_REVEAL_DELAY` after the cursor enters a new *buffer line* (not block); `RenderedView` keeps the block rendered and draws an inverted-cell cursor indicator meanwhile. The app loop's `rx.recv_timeout(60 ms)` fires the redraw without a keypress.
- **Single-pass parse.** `ParsedDoc::build` gets blocks and top-level byte ranges from one `parse_raw_with_ranges` call (a `RangeTracker` observes the same offset-iterator events), so blocks↔ranges stay 1:1 by construction. A second `top_level_block_ranges` pass costs a full extra parse per reparse.
- **Block-level render memoization.** `EditorState` owns a `markdown::RenderCache` threaded into every `refresh_parsed`. The key is the `Block` *value* plus a render-settings fingerprint (theme address, viewport width, `table.row_striping`, big-H1, …); keying by AST rather than source bytes keeps live table-width drags and post-pass mutations correct. `Block::ImageBlock` is never cached (its row count tracks the decode cache). Eviction is by document membership per build. **A new `Renderer` knob that changes output must go into `RenderSettings`**, or stale hits paint with the old setting. The measurements behind it — the frame budget, the per-stage costs, the ceilings that remain — are in [`docs/dev/performance.md`](docs/dev/performance.md).
- **One shared `line_render` module.** Preview and Rendered both call it; the trailing-cell fill and word-aware wrap live there. Change it, don't fork it.
- **Where a row may break is one predicate.** `line_render::is_break_after`: "anything non-alphanumeric", narrowed by three refinements (issue #36) — a no-break char (U+00A0 and friends) is never a break; an *opening* delimiter (`(` `[` `{` `“` `‘` `«` `¿` `¡`, plus `"`/`'` when a word follows and none precedes) is never one, so it can't hang alone at the row edge; and `.` `,` `:` `'` `’` `_` are not breaks between two alphanumerics, keeping `they’re`, `3.14`, `12:30`, `file.md` whole. **`/` is deliberately excluded** — including it strips every break point out of a URL path, and links are far more common in Markdown than `and/or`. Both neighbours matter, so the predicate takes the slice and an index, not a lone `char`. A break right after a one-letter word backs up to the preceding break (`ends_with_lone_word`) unless that word starts the row. Smart punctuation is on, so a rendered contraction carries `’` (U+2019) — a rule naming one owes the other.
- **A row may never end mid-grapheme-cluster; the cluster gate outranks every break refinement.** The wrap reasons in `char`s, where a ZWJ looked like a fine break (a family emoji split across rows, a combining mark stranded from its base). `cluster_starts` builds a boundary mask once per line, consulted by both `is_break_after` and `snap_to_cluster_boundary`. Two things keep it affordable and terminating: an **all-ASCII fast path** returns `None`, and a snap that would empty the row **keeps the unsnapped break**. This fixes *breaking* inside a cluster, not *measuring* one — `char_cells` still sums a ZWJ sequence's members.
- **A break absorbs the single space that follows it, so `next_start` may exceed `row_end`.** A space at a row *start* reads as accidental indentation. `absorbed_next_start` applies to every arm, not just the hard break. The absorbed char belongs to no row, so both cursor paths know it: `sub_line_of_col` reports a column in `end..next_start` as the **next row's column 0**, and `render_line_reporting_cursor` rewrites a `cursor_col_override` landing there onto that row's first char (otherwise the cursor sits on a cell that doesn't exist). A *run* of spaces is never absorbed (interior whitespace is content — `visual_rows_preserves_interior_whitespace_across_wrap`), nor is a trailing one. Overlay painters intersect with `[row_start, row_end)`, so an absorbed char is never washed.
  - **`line_render::last_col_in_row` is the single clamp keeping a cursor on its own row**, shared by `state_cursor_visual::raw_col_for_visual_cells` and `mouse_ops::coord`'s `char_in_row_at_cell`, `non_table_click_to_raw_col`, `click_to_rendered_char_idx` and `rendered_click_to_line_col`. It measures against `end`, never `next_start`: `next_start - 1` clamps the cursor onto the absorbed space — a char with no cell, so Up stalls permanently and a click on a row's last cell lands a row low. A new screen-cell→char-column site owes it the call.
- **The cursor is a uniform block; color, not shape, signals context.** The cell at the insertion point is recolored while the character stays visible. Resolved in one place — `app::cursor_style::editor_cursor_style` — with views receiving the finished `Style`. The default handler colors by *view* mode (`status_mode_preview` / `_rendered` / `_raw`); under vim the cursor **mirrors the sub-mode chip**, reading the same `status_mode_vim_normal` / `_insert` / `_visual` fields (minus the chip's `BOLD`). RAW is surfaced only in INSERT; NORMAL/VISUAL keep their sub-mode color in every view. Modal inputs use `theme.cursor`. No bar/caret shape, no `CursorShape` enum.
  - Painted via `cursor_col_override`, never baked into the wrapped `Line`, so the wrap keys on glyph-free source text and stays in lockstep with `move_up_visual` / `move_down_visual` and the scroll math. `line_render::paint_row` recolors the resolved cell; the raw-reveal builders in `rendered_view/paint.rs` and `raw_view::raw_display_line` build lines without the cursor; `overlay_raw_cell` recolors a table cell in place. A block cursor on a selected cell wins over that wash.
- **Modal input cursors are blink-stable.** `ui::cursor::text_field_spans` always emits a one-cell slot — the character recolored when the blink is on, a plain cell when off — so the field never changes width. A new text-input modal must use it, or (where a value flows through `format_modal_row` / horizontal scroll and the cell can't carry its own style) mirror the constant-width slot with `cursor::CURSOR_BLOCK`.
- **Code body rows render behind one pad cell, and three consumers must agree.** `render_code_block` paints each non-empty body line as `format!(" {:<width$}", …)`, so rendered column `c` shows raw char `c - 1`; an *indented* block adds the indent pulldown-cmark stripped. Both live in `markdown::code_layout` — forward for the two painters (`paint_byte_range_overlay`, `RenderedView`'s cursor indicator), inverse (`code_rendered_col_to_raw_col`) for `mouse_ops::coord`. Only the overlay had it once (issue #28). The cursor arm sits **ahead of the list arm** in the `visual_col` chain, or a code line reading `- foo` is claimed by the list-marker sniff.
  - **Fence rows are outside the mapping** (the opening row renders a ` lang ` label, the closing a placeholder): ask `is_code_fence_row`, then wash the whole row or leave the column alone. A **blank** body row still maps to the pad column, or the cursor jumps on the first keypress.
  - **`raw_lines` must come from `raw_source_lines`, never a bare `split('\n')`** — a block range ends with its newline, so the bare split appends a phantom entry. **The closing fence is identified by its *text*, not its index**: `is_code_fence_row` asks `is_closing_fence_line` (3+ of one delimiter, nothing else), because an *unclosed* fence — every code block while being typed — ends on ordinary code that still needs the mapping.
- **A code body line never de-renders, so "revealed ⇒ 1:1" is wrong inside one.** `code_layout::line_allows_raw_reveal` is the single derivation of which lines get raw source: every non-code line, a fenced block's opening fence plus a closing one actually typed, nothing in an indented block. `cursor_block_revealed()` deliberately doesn't know about it — it answers a block-level, time-based question for four other consumers. `RenderedView`'s reveal gate and `mouse_ops::coord` (click shortcut *and* `revealed_raw_row_count`) both ask the shared predicate.
- **NBSP padding in code blocks.** Blank lines inside fenced blocks use U+00A0, working around a ratatui `WordWrapper` (`trim: false`) bug where an all-whitespace line yields an extra visual row. Don't simplify back to spaces.
- **Word-group undo merging.** `History::record` merges contiguous single alphanumeric inserts into the previous delta; cursor moves break the group. Delta-based, not snapshot-based.
- **Visual line navigation.** `move_up_visual` / `move_down_visual` and `line_render::render_line` must use the same wrap algorithm (`visual_rows_of_str` / `sub_line_of_col`), or the cursor lands in a different column than where it appears.
- **`Action` is the full surface.** Every action lives in `config/keymap.rs::Action`; unimplemented variants are no-ops in `edit_ops` so keybindings stay stable while a feature is in flight.
- **Clipboard is feature-gated.** `arboard` sits behind the default-on `clipboard` feature; disabled, copy/cut/paste use the in-process kill-ring, which is also what tests assert against. Wayland needs `wayland-data-control` for read access.

### Frontmatter (YAML / TOML metadata blocks)

- **The block is rendered *verbatim*, and that is load-bearing rather than visual.** `parse_offsets::options_for` enables the matching metadata-block extension so `---` YAML and `+++` TOML become `Block::MetadataBlock` instead of the thematic-break-plus-setext-H2 pair that made a Hugo/Jekyll/Obsidian file's keys the loudest element on the page (issue #34). `render_metadata_block` emits **one rendered row per source line, every character in its source column** — rendering adds only color. That keeps the raw↔rendered column relation the identity function and the row count 1:1, which the raw reveal, the gutter's inverse and the scroll math all assume; a prettier treatment would owe every one of those a block-specific arm.
- **Four consumers must be told the mapping is the identity**, because their defaults are wrong here in different ways. `sub_lines_in_block` joins code blocks in the verbatim branch — a blank line inside frontmatter is data and renders a row, while the prose walk would drift the cursor up a row per blank. The overlay painter (`rendered_view::paint`) and the click mapper (`mouse_ops::coord`, via `LineMapping::Verbatim`) must not consult `InlineColMap`, which re-parses the line as Markdown (a quoted YAML value picks up smart quotes; a `*` in a glob opens emphasis). And `RenderedView`'s cursor-indicator `visual_col` chain needs its metadata arm **ahead of the list arm**, since `  - tag` is a YAML sequence entry the list-marker text sniff would shift. (`coord`'s list branch is AST-gated, so only the sniffing sites need the ordering.)
- **The delimiter lines are reproduced from `MetadataKind`, not stored** — pulldown-cmark hands the AST builder the inner text only, so a YAML block closed with `...` renders as a plain `---`. Same three columns, and entering the block reveals the true source.
- **The key/value split is cosmetic and deliberately shallow.** `metadata_key_end` finds the first `:` / `=` followed by a space or end-of-line, requires a non-empty key, and otherwise declines (so `- https://example.com` doesn't split at the scheme's colon). It must not become a YAML or TOML parse: the two spans always concatenate back to the source line byte for byte, which is what makes the identity mapping true.
- **The export path applies the same gate.** `export::html` keeps its own base option list and takes the metadata half from the shared `metadata_options_for`; without it an export reproduces the misparse. pulldown-cmark's HTML writer treats a metadata block as non-writing, which is also the wanted behavior.
- **The extensions are enabled per *document*, gated on its first line.** Unconditionally on, pulldown-cmark claims *any* later `---` line followed by non-blank text and eventually closed by another `---`, so an ordinary section separator (a rule above a heading, a Marp slide break) parses as metadata — dim key/value styling, `block_allows_inline_markdown_at` refusing emphasis inside it, and *nothing* emitted by the HTML writer, silently dropping content from the export. Every parse of a document — AST, offset scan, HTML export — must pass *that document's* text through `options_for`, or the 1:1 blocks↔ranges pairing breaks.
- **A `---` is still a rule almost everywhere.** Every `---` past the first line is one unconditionally; even the opening one is frontmatter only when the delimiter run is exactly three characters, the line below is non-blank, and a closing delimiter exists. `edit_ops`'s inline-snippet gate excludes the block: emphasis or a link inside frontmatter is data corruption, not formatting.

### Blockquotes

- **The quote's style is a *base*, never a replacement.** `render_blockquote` renders inner blocks first, then prefixes each line with the `▎ ` bar, so every span arriving there has resolved its own style; overwriting them with `blockquote_text` silenced bold, italic, code spans, highlights, strikethrough and link color inside any quote (issue #33). Each span is now `base.patch(span.style)`, with the inner block's own line style (a nested code block's surface) layered into `base` first so it still wins. A new decoration wrapped around already-rendered lines owes the same shape.
- **`blockquote_text` is a background wash, not a text attribute** — a blanket ITALIC leaves `*emphasis*` inside a quote with nothing to say. It is `secondary` mixed almost all the way to `bg` (`QUOTE_BG_MIX_TOWARD_BG`), the same `blend` that is a no-op for non-RGB palettes, so `dark_256` / `light_256` pin it by hand and `Monochrome Dark` uses DIM.
- **The wash is carried by the *line* style, not by padding.** `line_render` fills a row's trailing cells with `Line::style`, extending the wash to the viewport edge and filling a wrapped continuation's indent zone (the bar is repainted there by `leading_bar_prefix`). Don't pad quote rows out to `viewport_width` the way `render_code_block` does — it would break the 1:1 raw↔rendered column relation.
- **The revealed row keeps the wash.** `RenderedView` resolves a `reveal_base` from the cursor block's AST kind and hands it to `paint::make_raw_line_over`; without it the row being edited drops out of the block it visibly belongs to (same reason a revealed mermaid body row gets `make_code_styled_body_line`). A new block kind painting its own surface owes an arm there.

### Syntax highlighting

- **The language comes only from the fence's info string, and the lookup takes only its first token.** No auto-detection, and none planned — guessing wrong recolors a document the author never asked to have recolored. `language_token` splits on `,`, whitespace and `{` so `rust,ignore` and `js {1,3-4}` resolve; the lookup is `find_syntax_by_token`, never `find_syntax_by_extension`, because a fence info string is a language name, not a path. The ` lang ` label row still renders the **whole** info string verbatim.
- **Token ranges are char indices.** syntect reports *byte* offsets, every column map in this crate is char-indexed, so `highlight.rs` converts once at its API boundary and a byte offset never escapes it — one that does puts every token boundary after a non-ASCII character in the wrong column (`ranges_are_char_indices_not_byte_offsets`).
- **`TokenClass` has no `Default` variant, and that omission is load-bearing.** Unclassified text produces no token, so "nothing to say", "unknown language", "over cap" and "setting off" are one path downstream: `code_body_row` with no tokens, reproducing the pre-feature single-span line character for character. That equivalence lets the existing code-block snapshots stand as the regression guard (`an_unknown_language_renders_exactly_like_highlighting_off`); a `Default` class would fork the plain path in two.
- **Classification walks the scope stack innermost-outward, and `storage` is a keyword.** A string's delimiter carries `punctuation.definition.string.begin`, which no rule claims, so the walk must fall outward to the enclosing `string.quoted.double`. All of `storage` maps to `Keyword`: TextMate uses `storage.type` for the keyword that *declares* something (`fn`, `int`, `var`) while an actual type name is `entity.name.type` / `support.type`.
- **Three caps, none redundant.** `MAX_HIGHLIGHT_SOURCE_BYTES` (64 KiB) bounds the *cold* parse; `MAX_HIGHLIGHT_LINE_CHARS` (2 000) bounds the *per-keystroke* cost, which the byte cap cannot, since incremental reuse needs an unchanged prefix and a one-line block has none; `MAX_HIGHLIGHT_GRAMMARS` (24) bounds grammar *compilation*, which is not a function of block size — syntect compiles a grammar's regexes lazily on first use (~9 ms, ~18 ms for Rust), so fifty one-line fences in fifty languages pass the other two caps and still cost ~430 ms of queued worker CPU. All three bound **color, never content**: over a cap the block still renders every byte, reusing the unknown-language path, because mermaid's refuse-to-render posture would be wrong for code a user must read. Tokenizing is the one content-handling path running *synchronously on the render thread*, so it is also wrapped in `catch_unwind`.
- **The grammar cap bounds a burst, not the process lifetime.** A flat lifetime counter locked a long session out permanently, and LRU eviction is backwards: syntect keeps compiled regexes in a `OnceCell` for the process's life, so re-using a grammar is free and evicting its record refuses a free grammar to admit a paid one. `GrammarBudget` splits the two questions: `warm` (already paid for?) only grows; `budget` (affordable *now*?) is a token bucket refilling one slot per `GRAMMAR_BUDGET_REFILL` and saturating at the cap, so a long idle can't bank slots. `refill` advances `last_refill` by the intervals actually consumed, not to `now`, or a document re-rendering faster than the interval never earns a slot. A third state, `pending`, stops the render thread re-queueing the same cold grammar every reparse. The rule is `GrammarBudget::admit`, with clock and cap injected so tests never touch the process-global `GRAMMARS`.
- **A refusal is also an event: `refused_grammar_retry_due` is what makes the burst bound true in practice.** Only a re-render re-asks `admit`, which for highlighting means `warm_generation` moving — and the queued burst compiles well inside one refill interval, so a document over the cap would stay partly plain for the session unless the user typed or resized. `GrammarBudget::refused` gives `tick_syntax_warm` a second reason to reparse, **edge-triggered** (`take_retry` consumes the answer), so a standing refusal costs one reparse per refilled slot. **That reparse only reaches the highlighter because it also bumps `highlight::retry_epoch`, which rides in `RenderSettings` beside `warm_generation`**: a retry is granted precisely when no grammar warmed, so nothing else in the fingerprint changed, every block hits the cache and `admit` is never re-asked — leaving the cap a session limit again with every `GrammarBudget` unit test still passing (`render_cache::tests::both_highlight_counters_clear_the_cache`).
- **Parsing is synchronous and compiling is not, and the asymmetry is the design.** Tokenizing stays on the render thread because highlighting changes only *color*, on text already on screen: any deferral must paint something during the gap, and both options are bad — plain text drops colors out and back on every keystroke, and stale tokens are char ranges, so an insert shifts every color on the line. A debounce was rejected on the same argument plus one of its own: `"`, `` ` ``, `/*` and `#` reclassify the rest of a block in one keystroke, so a heuristic waiting for whitespace holds the stale render exactly when it is most wrong. Compilation is the exception because it happens once per language: `spawn_warm_worker` owns it, a cold grammar returns `Admission::Queue`, the block renders plain, and the worker replays *the block's own lines* — syntect compiles per **match pattern**, so replaying the real block compiles exactly the patterns the render thread is about to need. A pattern the warm parse missed compiles one regex inline; that residual is accepted. A warm parse that panics leaves the grammar `pending` forever — plain, rather than retried into the same panic every frame.
- **`warm_generation` is how a plain block ever becomes colored, and it must ride in `RenderSettings`** — warming changes no `Block` value, so `RenderCache` would serve the plain render for the life of the document. `App::tick_syntax_warm` polls it on the 60 ms loop tick (polled, not pushed: `markdown` sits far below `app` and must not learn about `AppEvent`). `App::syntax_warm_generation` is seeded from the live counter rather than 0 (a second `App` in one process must not see a spurious first-tick change), and that read is taken **before** `spawn_warm_worker` and `configure_new_editor`, not at the struct literal — the constructor's own first render queues this document's grammars, and a later read can capture a landed compile *as* the starting value, leaving the block plain until some unrelated reparse. The renderer reads the counter itself and pins it to 0 when the feature is off, so toggling can't leave a stale generation in the fingerprint.
- **Asynchronous compilation makes highlighting eventually-consistent, which tests must opt out of.** A bare `highlight_block` on a cold grammar answers `[]`, so a color assertion either races the worker or passes because an unrelated test warmed that grammar first. `warm_inline` marks a grammar usable immediately, compiling on the calling thread: every classification test goes through the `hl` helper and both `render_highlighted` helpers call `warm_fence_languages` first. Production code must never call it on the render thread.
- **Incremental reuse is two-sided, and the convergence check is what makes it correct.** The cache holds, per block, the `(ParseState, ScopeStack)` at the *start* of each line plus a tail entry for the state after the last (without the tail, appending at a block's end could not resume). Lines before the first change carry over directly; after it, the parser position is compared against the cached position at the matching line (re-based, since an edit adds or removes lines), and once the two are equal *and* the remaining text is unchanged, the rest carries over. **Both halves of the position are needed** — `ParseState` omits the scope stack, and resuming with a fresh one misclassifies everything below the edit. The invariant tests assert is "the incremental result equals a cold parse"; `reuse_is_actually_happening` guards the other direction, so a cache degrading into a full re-parse can't leave every correctness test passing.
- **`syntax_*` theme styles are patched over `code_block_text`, never used alone.** Each sets a foreground only; the code surface owns the background, and a syntax style with its own `bg` paints a stale one wherever a theme moved that surface (`syntax_styles_carry_no_background_of_their_own`). All seven derive from existing `Palette` slots, so every built-in gets a coherent set with no per-theme authoring; only `monochrome_dark` has hand-written entries, marking just `Keyword` and `Comment` since with no color to spend, attributing everything distinguishes nothing.
- **The seven slots must be *foreground* slots, and the derivation is contrast-checked.** A palette splits into text carriers (`primary`, `text_muted`, `link`, `success`, `warning`, `error`, `code`) and fills/chrome (`secondary`, `accent`, `bg` / `surface`); only the first group has had to be legible as characters. `syntax_type` was `secondary` and `syntax_function` `accent`, measuring 1.99:1 and 1.51:1 against `dark_256`'s code surface versus 6.97:1 for the plain code text they replaced — highlighting made code *less* readable, on the very theme the indexed fallback substitutes into. They are now `code` and `link`, with `error` taking `attribute`; `themes::util::legible_on` is the backstop for the rest, lifting each color toward `text` until it clears `SYNTAX_MIN_CONTRAST` (4.5:1) while keeping its hue.
- **`legible_on` is a no-op for indexed colors, so `dark_256` / `light_256` pin all seven by hand** — the same reason those files already pin the heading ramp, `code_bg`, `selection_muted` and the diff washes. Their picks are the bright- (or dark-) tint siblings of the slots the RGB derivation would use, since the mid shades are chosen to read on `bg`, not on the code surface; `light_256` diverges further (no dark orange in the cube clears the floor, so `keyword` takes the conventional deep red and `attribute` moves to teal). `syntax_contrast_clears_the_floor_for_every_builtin_theme` holds all 27 themes to account, resolving the xterm cube itself and treating an ANSI 0–15 index as a failure rather than a skip. Its floor is `min(SYNTAX_MIN_CONTRAST, plain code text)`: a theme cannot make a token more legible than its own body text, and the promise that matters is that highlighting never makes a block *less* readable than plain.
- **The mermaid source reveal is out of scope, not unfinished** — `make_code_styled_body_line`'s one call site always has the language `"mermaid"`, and no Mermaid grammar exists in either syntax set, so threading tokens through it would be provably inert (`mermaid_has_no_grammar_so_that_surface_stays_out_of_scope`).
- **`syntax_highlighting` must be in `RenderSettings`** — the `Block` value is unchanged by the toggle, so without the fingerprint field a cached hit repaints with the old setting. It reaches `EditorState` through `app::configure_new_editor`, like `big_h1` and `cursor_blink`, so a document opened by following a link gets it too.

### Footnote reference markers

- **The marker is plain ASCII: `renderer::reference_marker` renders `[^label]` as `[label]`.** Superscript (`⁽¹⁾`, U+207D/U+207E) is missing from most monospace fonts, and a proportional fallback draws the parenthesis wider than the cell (ghostty shrinks only a curated codepoint list; iTerm2 and Terminal.app clip instead, which made it look terminal-specific rather than font-specific). The superscript digits carried a second problem: `¹²³⁴` are East Asian Width **Ambiguous** while `⁰⁵⁶⁷⁸⁹` are Neutral, so a terminal treating ambiguous as wide measured footnotes 1–4 a column wider than edamame did. A marker glyph outside Basic Latin must be justified against font coverage *and* width class (`footnote_marker_is_plain_ascii`).
- **Adjacent references fuse into one marker, and three places must agree on how.** `[^1][^2]` renders `[1,2]`. `renderer::footnote_run_at` is the single derivation; `render_inlines` and `rendered_inlines_char_width` both consume it so painted marker and measured width can't drift, and `render_paragraph` splits at breaks and calls back through `render_inlines` rather than walking inlines itself. "Adjacent" means adjacent *inlines*, so `[^1] [^2]` stays two markers.
- **`InlineColMap` collapses a fused run by two chars per abutting reference, not one.** A lone `[^1]` → `[1]` differs by exactly the dropped `^` (hence `collapse_footnote_refs` being a single `retain`); a fused run additionally drops the second reference's `[`, and the entry surviving at that position is the *previous* reference's `]`, which becomes the rendered comma. Drop only the carets and the map runs one column long per fused pair, so every selection projection and click past it lands short (`adjacent_footnote_references_collapse_into_one_marker`, `click_inside_a_fused_marker_follows_the_label_clicked`).

### In-app documentation

`docs/*.md` is compiled into the binary (`src/docs/registry.rs`) and opened as a pathless, read-only document.

- **`open_doc` and `file_path` are mutually exclusive, and pathless is what makes a page safe.** Both load paths maintain it — `load_doc_into_editor` sets one and clears the other, `load_file_into_editor` the reverse. `handle_file_changed` / `handle_file_removed` return early unless `file_path` names the changed path, so an external write landing while the manual is open is dropped rather than diffed against it; the watcher deliberately stays armed on the file the reader came from. Forgetting the clear also leaves `follow_link` resolving a real document's relative links against the embedded manual.
- **A relative link resolves against the embedded set only while a page is open.** The gate is `open_doc.is_some()` at the `follow_link` call site, never inside `LinkTarget::parse`, which is pure and must keep answering the same way for a document linking to a file of its own named `security.md`. A path with any directory component (`dev/theming.md`, `../SECURITY.md`) is not embedded and becomes a GitHub URL.
- **Read-only rests in `Mode::Preview` and is enforced by two backstops, not per-site guards.** Preview is already the browse-only view (no cursor, no raw reveal, `mouse_ops::apply_preview_action` declining the checkbox toggle and table handles), so `edit_ops::enter_edit_if_preview` refusing the transition out of it makes all twenty-six of its call sites — `Action::Paste` among them — no-ops at once, and `EditorState::apply_delta` refuses the write. `ToggleRawMode` / `EnterEditMode` no-op in `edit_ops` too, since they *request* the transition rather than incidentally causing it. The App-level `actions::readonly_safe_action` is a courtesy on top, and a rule over `ActionCaps` rather than a list: it denies `mutates_buffer || needs_path` (five actions) so a palette pick of `Save` doesn't open a Save-as prompt for a document nobody can own, allows `navigates_away` emphatically, and refuses **silently**. Keyed on `editor.readonly`, not `open_doc`.
- **A context-dependent action is normalized *before* any gate sees it.** `Alt+Left` / `Alt+Right` bind to `TableMoveColumnLeft` / `TableMoveColumnRight` — "reorder a column" inside a table, "navigate back / forward" outside one. Behind the gates the redirect left readers a dead chord, so `App::normalize_context_action` runs ahead of all three. `cursor_in_table` (both copies — `app::actions` and `ui::bottom_region`) answers `false` while `readonly`, so a `GoToSection` jump into one of `keybindings.md`'s tables can't kill `Alt+Left` and the hint row keeps the Back chord unconditionally; that row otherwise differs by one field, dropping only the `Press any key to edit` prelude.
- **`ALL_DOCS` derives the index page and link resolution; it does not derive the palette** — `ui::command_palette::actions::ALL_ACTIONS` is hand-written, so a new page needs a line there too (`the_palette_lists_every_embedded_page_exactly_once`). Fragments match exactly, like every other deep link, so a renamed heading breaks sibling pages' links silently and only in the app (`tests/docs.rs::every_cross_page_fragment_names_a_real_heading`).

### Inline links in modal bodies

A modal can carry clickable, Tab-focusable links in its prose — `ui::modal_links` owns the mechanism, `app::modal::docs_link` the one-line "see the manual" footnote built on it.

- **A link-bearing modal wraps its own body; every other modal still does not.** ratatui's `WordWrapper` is private and `Paragraph::line_count` answers a count, never a mapping, so there is no way to ask where a span landed. `wrap_rows` ports `WordWrapper` for `trim: false` and the pre-wrapped rows are painted with **no** `Wrap` set, so a residual disagreement clips a trailing cell instead of reflowing rows out from under the rects computed beside them; an empty `links` slice takes the old path verbatim. The port owes the body more than row breaks: `wrap_one_line` folds each line's style into every piece and copies its alignment onto every row it produced, and `link_rects` derives its own offset via `row_start_col`, or a centred row paints where the hit-test isn't. Pinned by `wrap_matches_ratatui_paragraph_wrapping` and `a_centred_link_hit_tests_where_it_is_painted`, both reading real renders back.
- **Link identity is structural — `(line_idx, span_idx)` — never inferred from style.** `ui::markdown_cheat_sheet` styles illustrative snippets with `theme.link_text` because they *depict* links, and `monochrome_dark` spends `UNDERLINED` on H2–H6 as well as every link slot. Either sniff would hand the user a clickable affordance resolving to nothing.
- **`ModalLinkTarget` is deliberately not `LinkTarget`.** `Anchor` and `Footnote` would resolve against whatever document sits behind the overlay, and a `LocalFile` naming a manual page is redirected to the embedded set *only while a page is already open* — so from a modal it would resolve `keybindings.md` against the working directory and open whatever sits next to the user's shell. It is a **struct**, not an enum: a modal link goes to a manual section and nowhere else. It briefly carried a second `Url` arm for an address handed to the browser, which no modal ever declared — add that back *with* its caller, not ahead of one.
- **Only *informational* modals get a footnote.** On a modal that asks a question, following a link closes the prompt — and closing the media prompts *is* an answer ("no, this session"). A modal with dismissal bookkeeping builds its own outcome instead of calling `follow_and_close`, so the bookkeeping still runs. Each footnote is a named `DocsFootnote` const so `the_docs_link_names_a_heading_that_exists` can resolve its fragment against the real page.
- **Tab walks one ring: links first, then buttons.** `focused` keeps meaning "focused button index" with `focused_link` beside it, so existing modals read state unchanged; `y`/`Y` stays a shortcut for the focused *button* only. `LinkableResponse` wraps `ModalResponse` rather than adding a variant, which would be a compile error in every modal that will never carry a link. Following a link needs viewport dimensions that only `handle_key` carries, so `App::follow_modal_link` reads the `last_doc_height` / `last_doc_width` refreshed each frame in `prepare_viewport` rather than changing thirty-six `handle_click` signatures — and routes a manual page through the dirty guard, since opening one replaces the document.
- **A modal link is not an `Action`, so it must re-state the gates it bypasses.** `follow_modal_link` is a close-callback, which is exactly what puts it outside `diff_safe_action` — the gate that makes navigating away mid-review impossible everywhere else. That is reachable: `App::new` pushes the config-warning and capabilities notices *before* `main` calls `enter_read_only_diff`, so a link-bearing modal sits over a `git difftool` review on the first frame. Ungated, following one discarded the review with no confirmation *and* recorded a nav entry stamped `Mode::Diff`, which `restore_nav_entry` re-applies verbatim to a fresh editor holding no `DiffState` — a blank document area under a diff hint row. So it is refused with `flash_action_unavailable("diff review")`, not with the quit-confirm modal: a review is abandoned only by an explicit decision, and clicking a footnote is not one. The refusal is written against *replacing the live document*, which is what every `ModalLinkTarget` does today; a target that merely handed a URL to the browser would be safe mid-review and would owe an arm of its own. A second gate a modal callback can skip owes the same treatment here.

### Search and replace

- **The flow is gated on `EditorState::search.is_some()`, not a `Mode` variant.** Unlike diff (which replaces the whole view), search keeps the document rendering in the current view mode with highlights on top, so a `Mode::Search` would force an "effective view mode" indirection through every render-dispatch site.
- **Only a *replace* flow captures input; a navigate-only flow is a non-capturing overlay.** `App::search_flow_captures()` is `search.as_ref().is_some_and(|s| s.is_replace_flow())`, in vim and default mode alike. A replace flow needs the unmodified `Tab`/`r`/`a` keys, so it traps input at three choke points: `DefaultHandler::handle` intercepts the hard-bound flow keys (`search::search_keys`, the table-driven pattern `diff_keys` mirrors); `App::dispatch_action` default-denies everything off the `search_safe_action` allowlist *before* `handle_app_action` runs, flashing via `flash_action_unavailable`; `dispatch_mouse_event` drops all mouse input but wheel scroll and pointer moves. The allowlist covers the flow keys, read-only navigation (cursor moves, selection, `SelectAll`, `Copy`) and the always-safe set (scroll, overlay openers, save, quit, in-flow undo/redo), so a new buffer-mutating action is denied automatically. A **navigate-only** flow (vim's `/`, `Ctrl-F` with an empty replace field) does not capture: only `Tab`/`Shift+Tab` (plus vim's `n`/`N`) and `Esc` are intercepted ahead of the keymap — `DefaultHandler` returns only `SearchNext`/`SearchPrev`/`SearchExit`, `dispatch_action` routes just those to `dispatch_search_action`, and everything else falls through to normal editing.
- **A non-capturing flow's match list is refreshed every frame** — it allows edits outside the in-flow mutation paths, so `prepare_viewport` calls `ensure_search_fresh` each frame (version-guarded → a no-op when nothing changed).
- **Search exit is a motion — no scroll-back.** `exit_search` just drops the session, leaving cursor and viewport on the match the user navigated to.
- **Vim `/` `?` search is incremental.** `vim_ops::incsearch::update_incsearch` rebuilds a real navigate-only `SearchState` on every keystroke (typed, history-recalled or pasted — all three through `feed::cmdline_live_update`, shared with the `:s` preview), parks the cursor on `SearchState::focus_relative_to` (the same method submit uses) and scrolls it into view. Because the transient session *is* `EditorState::search`, the hlsearch painters, hint counter and raw-reveal suppression work unchanged — no incsearch-specific render code exists. `IncsearchSession` stashes the pre-prompt cursor/scroll and any prior hlsearch session; Esc restores all three, and Enter restores them *before* the `EnterSearch` outcome so the submit resolves against the original cursor, byte-identical to a preview-less submit. Incsearch never touches the buffer. The shared view primitives — `place_cursor`, `restore_view`, `scroll_cursor_comfortably_into_view` (the one TOP_MARGIN core behind the hunk/match focus scrolls too) — are the single implementations; don't hand-roll a cursor park or a context-margin scroll.
- **Match freshness is version-keyed.** `SearchState` stores byte ranges valid for the `Buffer::version()` they were computed against; every in-flow mutation (replace, replace-all, undo, redo) calls `ensure_search_fresh` afterwards. The render layer additionally clamps ranges against the live source so a stale list can't panic — don't rely on that. Wholesale content swaps (`replace_buffer`, diff entry) drop the session entirely.
- **Matching is smartcase for navigation, case-sensitive for replace.** `ensure_fresh` picks by `is_replace_flow()`: navigate uses `find_all` (case-insensitive unless the pattern has an uppercase char), so *every* user gets smartcase, not just vim; replace uses `find_all_cs`, so a lowercase find term never rewrites a casing variant the user didn't type. `find_all_ci` compares char-by-char against the **untouched** haystack so offsets stay on char boundaries for multibyte text. There is deliberately **no regex** in `/` search; regex is confined to `:s`/`:%s`.
- **The query is escape syntax, so `query` and `needle` are different strings.** Search stays literal-substring, but a one-row field can't hold a line break — so `search::escape` gives the query vim's backslash convention (`\n` `\t` `\r` `\\`), and `SearchState::new` splits input into the typed `query` (kept verbatim for *display*) and the decoded `needle` (what `ensure_fresh` matches); `replace` / `replacement` are the same pair. **Match with `needle`, display `query`** — swapping them either searches for a literal `\n` or carries a raw newline into a one-line surface. An unrecognized backslash is a `SearchError`, not a silent literal: `SearchState::new` returns `Result`, the modal reports it with focus on the offending field, `enter_vim_search` flashes it, and incsearch shows nothing (mid-typing, every prefix of a valid query is briefly invalid). **Text edamame supplies rather than the user types must go through `escape::escape` first** — `feed::search_word_outcome` (`*` / `#`), `search_modal::paste`, and `cmdline::paste_str` on a *search* prompt (`CmdLineKind::is_search`; an `:` prompt keeps the plain newline strip).
- **A match may span a line break, so no highlight consumer may assume one range sits on one line.** `RawView` clips every range (search, `:s` preview, yank flash) to the line being painted through the shared `push_clipped`; `paint_byte_range_overlay`'s per-raw-line intersection does the same for Rendered / Preview; `paint_search_overlays` re-selects overlapping matches per *block* so a match straddling two blocks paints in both.
- **Replace keeps the reveal beat.** A single replace goes through `apply_delta` (one undo delta) plus an immediate `flush_parsed_if_dirty` (overlays and match recompute need fresh source-map ranges next frame), refocuses past the inserted bytes (so a replacement containing the query can't trap the flow) and arms `search_advance` — mirror of `diff_advance` — so the cursor jumps to the next match only after a 350 ms reveal. Replace-all is a single coarse `EditDelta` on the normal history stack, preserving prior undo history unlike the diff merge's `reset_with`.
- **A replace flow leaves Preview** (browse-only): `enter_search_flow` transitions Preview → Rendered when the replace field was filled. Navigate-only flows and zero-match queries leave the mode untouched. **A read-only document drops the replacement at that same entry point**, so the flow it gets is navigate-only. Both halves matter: a capturing flow would hold `Tab` / `r` / `a` for commands `readonly_safe_action` then denies, taking the reading keys with them; and the mode transition is a bare `editor.mode = …` that neither `enter_edit_if_preview` nor `apply_delta` can refuse, since the modal reaches `enter_search_flow` directly and no gate over `Action` ever sees it. Dropping the replacement makes that branch unreachable rather than merely unproductive, and here is the one place to do it — every caller (the modal, vim `/`, the tests) passes through. Unlike the silent `readonly_safe_action` denials the drop is flashed: the user typed the replacement into a field the modal offered them.
- **Raw reveal is suppressed during search**, so blocks don't flip between rendered and raw under the highlights as the user tabs through matches.
- **Highlight painting is shared.** Rendered + Preview paint through `paint_search_overlays` → `paint_byte_range_overlay` (the generalized former `paint_selection_overlay`), called from `EditorView` as a post-pass; Raw paints per-char inside `RawView`. Focused match → `theme.selection`, the rest → `theme.selection_muted`. The painter's block-kind prefix shifts (heading space, code pad cell) resolve the block via `ParsedDoc::real_block_for_byte` — **never index `parsed.blocks` with a `source_map` block index**; the source map counts blank-line virtual blocks, so the index spaces diverge in any document with blank lines.

### Live `:s` substitution preview (vim `inccommand`)

- **The preview transiently rewrites the real buffer — through raw `Buffer` edits only.** While the vim `:` line holds a complete-enough `:s`/`:%s`/`:'<,'>s`, `vim_ops::preview::update_substitute_preview` applies it via raw `Buffer::insert`/`remove` (never `apply_delta`), so no undo delta is recorded and `dirty` is untouched. Every keystroke reverts the previous preview and recomputes against the pristine buffer — never diff two previews. On Enter the reducer reverts *before* `submit_ex`, so commit semantics stay byte-identical to a preview-less submit. `SubstitutePreview` lives on `EditorState` (like `search` / `yank_flash`) so painters read it off `&EditorState`.
- **The revert delta is version-stamped as a fail-safe** — a revert on a mismatched version silently drops the preview instead of corrupting text, and `replace_buffer` drops any preview. Don't rely on the stamp: any new mutation path reachable while the cmdline is open must be gated.
- **Three gates hold while `substitute_preview.is_some()`.** (1) `tick_autosave` / `autosave_deadline` skip entirely — raw preview edits bump `version` without touching `dirty`, so on an already-dirty buffer the debounce would write preview text to disk. (2) `dispatch_mouse_event` blocks everything but wheel scroll and pointer moves (shares the capturing-search gate) — a click or checkbox toggle would mutate text that is about to revert. (3) `prepare_viewport` skips `ensure_search_fresh` and both search-overlay painters early-out, since a coexisting hlsearch session's ranges are stale against preview text (the session survives and repaints after the revert). Keyboard needs no gate — the cmdline captures every key. Additionally `cursor_block_revealed()` returns false while a preview is active: it parks the cursor on the first affected line, and the reveal delay would elapse mid-typing.
- **A `:s` pattern sees the whole resolved range at once, not one line at a time.** `ex::region_haystack` materializes lines `first..=last` as one string, and `ex::for_each_region_match` is the *single* match-finding implementation driving the commit path, the replacement preview and the highlight-only preview — which makes "what the preview highlights" and "what Enter replaces" the same set by construction. Four load-bearing details: (1) **`multi_line(true)` at both compile sites** (`execute_substitute` and `compute_preview_plan`) keeps `^`/`$` anchoring per line — setting it on one and not the other makes the preview lie; `dot_matches_new_line` stays off so `.` refuses to cross a break. (2) **The region excludes the last line's own break**, which is the entire enforcement of the range bound: a `\n` pattern can never reach past the named lines. That costs one deliberate divergence from vim (a single-line `:s/\n//` can't join with the next line); `:%s` resolves `last` to ropey's phantom line, so it *can* consume the file's final newline. (3) **The non-`g` walk replaces the first match *starting on* each line**, resuming at the line after the last line the match covered, with a correction for a match ending exactly at a line start (any pattern ending in `\n`) — without which every other line is skipped. (4) **`match_cap` stops on a match boundary, not a line boundary**, so the preview's `removed` stays a verbatim prefix of the region. Don't reintroduce a per-line `substitute_line`.
- **Compute is pure and shared with the commit path.** `ex::build_substitution` produces the single `EditDelta` plus post-apply ranges of each inserted segment; `preview::compute_preview_plan` is a pure function of `(Buffer, cursor_line, Substitution, visual_range)` — the unit-test seam. `Substitution::replacement_present` (did the user type the second delimiter?) distinguishes highlight-only `:%s/foo` (ranges, first per line without `g`, no edit) from deletion preview `:%s/foo/` (edit applied, zero-width ranges filtered).
- **The preview regex is bounded; the commit regex is not.** The preview compiles `fancy-regex` with `backtrack_limit(100_000)` and caps the walk at 1 000 matches (later lines stay original until submit), so a pathological half-typed pattern fails fast per keystroke. Parse/regex errors and matchless patterns silently end the session — never flash an error mid-typing. Painting reuses the search walk (`paint_substitute_preview_overlays`, an inline branch in `RawView`), all ranges in `theme.selection` — no focus concept, matching nvim's one `Substitute` group.

### Vim commands inside a table

A rendered GFM table's `|` delimiters and alignment row are auto-managed chrome, not prose, so the vim layer treats the *cell* as the unit a motion moves within and the *row* as the unit a line command acts on. All of it lives in `editor::vim_ops::table`.

- **Raw mode is exempt, and gets that for free** — every query funnels through `table_edit_ops::current_table`, which returns `None` in `Mode::Raw`.
- **The scoped resolvers replace the bare ones at the input layer.** `resolve_scoped_motion` / `resolve_scoped_op_range` stand in for `motion::resolve_motion` / `resolve_motion_range` throughout `feed.rs`, rather than each call site clamping the result, so a new operator target can't forget the clamp; `motion.rs` stays pure and buffer-only. The check is `rg 'resolve_motion(_range)?\(' src/input/vim/feed.rs`, which should match nothing. `;` / `,` resolve through `resolve_find_repeat` and apply `scope_offset` by hand — the one exception.
- **Clamping shapes the keystroke; `range_breaks_a_table` is the safety net.** A range reaches a header or alignment row by plenty of routes with no cell to clamp against (`2dd`, `dj`, a VisualLine selection whose cursor left the table, a charwise selection carried down by `j`, `Vp`, Visual `r`), so the guard is asked of the **range**, immediately before the mutation, at the two funnels every vim range edit passes through — `run_operator` and `run_visual_operator` — plus the paste and replace sites. A new vim mutation path must call it too. `Yank` is never refused; it mutates nothing.
- **A charwise Visual highlight must cover only the cell's content — horizontally.** The span includes the char under the cursor, so the *horizontal* clamp is one grapheme tighter than in Normal: `CellLimit::LastChar` (vs. `Append`) stops `$`/`w`/`f` on the cell's last character, and `h`/`l` route through `visual_cell_step`; `feed.rs` derives both from the single predicate `is_charwise_visual`. Operator ranges keep `Append` (exclusive end — `D` must clear the whole cell). The guarantee is horizontal only: `j`/`k` and the deliberately unscoped document motions still leave the cell, which is what the range guard is for.
  - **The two halves answer different failures.** Crossing a `|` promises an edit the guard refuses, so there the clamp keeps the highlight honest. Reaching the append slot is *not* refused: `table_break` measures confinement against `Cell::content_end` (the **untrimmed** span between the pipes) while `CellScope::end` is trimmed past the last non-blank, so the padding between them is inside the cell as far as the guard is concerned and the edit silently eats it — cosmetic rather than structural, but the clamp is the only thing preventing it.
- **Both doors into charwise Visual owe the same append-slot pull-back, on both ends of the span.** `enter_visual` (`v`) and `toggle_visual_mode` (`V`→`v`) each call `visual_endpoint_in_cell`, which resolves against the *endpoint's own* cell rather than the cursor's — `V`, `$`, `v` parks the cursor on the slot, and an `o` in between puts the anchor there instead, in a different cell. `v` needs only the cursor half; the toggle pulls cursor and anchor and re-syncs `EditorState::selection`, the span the operators actually read (`visual_charwise_range`), which still holds the pre-pull active end. A third entry into `VimSubMode::Visual` would owe all of it.
- **The guard refuses only what actually breaks.** Deleting a table *whole* is allowed, as are complete data rows, an edit confined to one cell's content, and an edit confined to the alignment row's own text (that row stays hand-editable, which is why it has no cell scope). Everything else — a partial span over a protected row, a range crossing a `|` — is refused with the reason on the flash line.
- **`dd`/`cc`'s structural routing is a convenience, not the protection.** `table_doubled_operator` re-routes an uncounted `dd` onto `table_edit`'s row delete and `cc` onto a cell clear, both through `execute_operator`/`fold_op_result` so register, single-delta undo and Insert transition come from the existing implementation. Counted forms deliberately fall through to plain linewise — safe *because* the funnel guard catches them. `TableOpOutcome` keeps "in a table, refused" distinct from "not a table, fall through"; collapsing them into an `Option` is what let `cc` blank the alignment row.
- **`p` picks a legal row boundary.** The ordinary linewise landing spot is *between the header and the alignment row* when the cursor is on the header, so `table_paste_plan` clamps the target index below the alignment row and refuses a register that isn't table rows (or a charwise one carrying a `|`). Raw mode keeps the plain landing spot.
- **Visual `p` asks about the payload, not the register.** `run_visual_paste` builds `text` first and hands `paste_over_range_refusal` that string plus the selection's linewise flag; passing `vim.register.{text,linewise}` lets both mismatches through (a `dd`'d row over a charwise in-cell selection carries `|` and a newline mid-cell; a charwise prose register over a VisualLine row replaces that row with a non-row). A new paste path owes the guard the bytes it is about to write.
- **Only the table's own lines are read out of the rope.** `table_edit_ops::table_at` slices the contiguous run of table-looking lines around a byte offset rather than calling `Buffer::contents()` — `cell_scope` is on the per-keystroke motion path.

### The vim command line

- **Every way a paste can reach an open `/` `?` `:` prompt goes through `App::paste_into_cmdline`.** There are two: a terminal bracketed paste (`Event::Paste`) and edamame's own paste chord, which used not to fire at all — an open command line captures every key, so the global keymap never ran and `Action::Paste` was swallowed by `feed_cmdline` (issue #17). `dispatch_single_key` now resolves *that one action* against the live keymap ahead of the vim feed — against the keymap, not a hardcoded `Ctrl-V`, so a rebound key works. Everything else stays captured.
- **The prompt is a single line, so a paste is transformed and bounded, in that order.** `cmdline::paste_str` escapes first on a *search* prompt (so a pasted break survives as `\n`) and drops any break the transform didn't consume; an `:` prompt keeps the plain strip. `PASTE_CHAR_CAP` is applied by `paste_into_cmdline` *before* handing the text over, and deliberately **not** via `ui::sanitize_paste`, which strips control characters and would eat the newlines the escape exists to preserve; the call site also keeps `input` below `ui` in the layer order. The cap is not cosmetic — `paste_str` inserts char by char through an O(n) `byte_index` scan, so an uncapped paste is quadratic (a 200 KB clipboard measured ~9 s of frozen UI).
- **A paste re-derives the live preview, exactly as typing does.** `paste_into_cmdline` calls `feed::cmdline_live_update` with the pre-paste input, so the `:s` preview and incsearch resolve against the new line; mutating `cl.input` without it leaves the preview describing text that is no longer in the prompt.

### Link following and deep links

- **A local link's `#fragment` is split off at classification time, not at dispatch.** `LinkTarget::LocalFile` carries `{ path, fragment }`, and `LinkTarget::parse` splits on the first `#` for both the bare-path and `file://` forms — every downstream question is asked of the path, and with the fragment attached `other.md#a-heading` has extension `md#a-heading`, so `is_markdown_path` said no and the link went to `open::that` (issue #38). A remote `Url` keeps its fragment inline.
- **One resolver answers "which heading is this fragment", it matches the GFM slug exactly, and both link paths use it.** `App::heading_line_for_fragment` is a plain lookup in `ParsedDoc::heading_anchors`, used by the in-document `#anchor` jump, the cross-file deep link and the startup anchor. **Do not add a normalizing fallback.** It briefly had one, so a hand-written `#Getting Started` resolved — not harmless: documents written in edamame travel, and a fragment that resolves only here ships broken to GitHub and every browser without ever failing locally (`only_the_gfm_slug_resolves_a_fragment`).
- **A deep link records one nav entry, not two.** `navigate_to_file` already pushes the origin as a `NavDest::File`, so the heading jump that follows calls `scroll_to_rendered_line` directly and deliberately does *not* `record_in_doc_jump` — otherwise one `NavigateBack` lands the reader at the top of a document they never saw.
- **The fragment must survive the dirty guard.** `DirtyGuardModal` must carry it alongside the pending destination (and through the save-as callback), or answering the guard opens the file at the top. Back/forward call sites pass `None` — a restored `NavEntry` has its own recorded scroll.
- **`navigate_to_file_at` owns the new document's viewport, so a caller must not re-assert cursor visibility on top of it.** It returns whether the file loaded, and the guard's Save and Discard arms skip their trailing `ensure_cursor_visible` on `true`: those calls correct the document the modal was *covering*. A fresh `EditorState` starts in `Mode::Preview`, where `scroll_to_rendered_line` moves `scroll` without moving the cursor — so an `ensure_cursor_visible` behind the jump sees the cursor at byte 0 above the viewport and scrolls back to line 0, discarding the fragment (`a_deep_link_answered_through_the_dirty_guard_still_lands_on_the_section`).
- **The command line splits its own `#section`, outside the parser.** `#` is a legal character in a file name, so `cli::split_startup_anchor` asks the disk (the literal path wins; only a path that doesn't exist gives its `#` up) and therefore cannot live in `Invocation::parse`, which is pure and unit-tested without an environment. `main` calls it between argument parsing and `App::new`; the injected-predicate inner function keeps the rule testable. It splits on the **last** `#`, so a directory carrying one still resolves.
- **The startup anchor is applied on the first frame, not in `App::new`** — the jump needs live document dimensions. `App::with_startup_anchor` parks it and `prepare_viewport` consumes it through `apply_startup_anchor` (the update notice's park-and-tick shape). It clears itself, so a later frame can't yank a reader who has scrolled away, and it records no nav entry.
- **A fragment naming no heading is reported, not swallowed** — the file opens and `App::flash` says the section wasn't found, since the document did load. The in-document `#anchor` path stays a silent no-op: nothing happened there at all.

### Diff review

A clean-buffer external write opens **diff review** (`Mode::Diff`): hunks stacked old-above-new with a decision divider each. Unchanged regions are painted as *rendered* Markdown; only changed regions drop to raw source. `src/diff/` owns the model, `ui::diff_view` the painting.

- **The rendered/raw split is a display partition, and it must never reshape `hunks`.** `layout::block_spans` partitions the new side by source-map block, marks blocks a hunk lands in as `touched`, and `build_visual_lines_rendered` emits a maximal run of touched blocks as one *raw region* and every other block as its pre-rendered rows. Snapping hunk ranges out to block boundaries instead collapses the per-row table hunks `engine::split_table_hunk` produces back into one whole-table hunk — the row-by-row review is the feature. A display-only partition leaves `hunks`, `decisions`, `HunkId` stability, `reconcile_with_disk` and `resolved_rope` untouched.
- **Every source-map block gets a span, zero-row blocks included.** A block rendering nothing (a standalone HTML comment, a `<!-- tui-columns: … -->` hint, a blank run collapsed by `preserve_blank_lines = false`) still carries source lines; without a span, a hunk confined to it marks nothing touched, falls inside no raw region, and its rows are never emitted — the user reviews a diff that doesn't contain the change while `all_resolved()` still lets them resolve it. Spans run from a block's own first line to the *next* block's first line (pulldown-cmark ranges absorb trailing blanks that already have virtual blocks), and the last to `len_lines()` including the phantom line, so the set is a total partition. A `debug_assert!` pins that plus "every hunk emits exactly one decision divider".
- **A new side that parses to *no blocks* falls back to the raw walk.** Reachable when the file was truncated to empty on disk, which the watcher hands straight through. With an empty partition the whole-document delete has no span, so the review would be blank with `all_resolved()` false and `Esc` refusing to finish a change the user was never shown.
- **`DiffState::parsed_new` is not stamped against `new_buffer`, so the one call that replaces the buffer drops the parse.** `build_visual_lines_rendered` reads source lines from the parse while taking the line count from the buffer, and nothing pairs the two. `DiffState` holds no theme and no width, so `reconcile_with_disk` calls `set_rendered_parse(None)` and lets `App::reconcile_diff_with_disk` reinstall a fresh one via `refresh_diff_parse`. A caller that forgets loses the rendered presentation until `refresh_parsed`'s tail call comes round; it never gets a review partitioned against stale line ranges. Don't replace the drop with a rebuild at the call site — the point is that the unsafe state is unrepresentable.
- **The initial build is deferred by one frame, on purpose.** At `enter_diff_mode` `viewport_width` still holds the *editor* width, which reserves a gutter `Mode::Diff` does not (`compute_doc_dims`), so a parse built there lays tables out against a width the diff view never paints at. It sets `diff_parse_dirty`, and `prepare_viewport` calls `flush_diff_parse_if_dirty` after posting the real width — so `parsed_new: None` is queried at least once per entry and is a live path, not a constructor artifact.
- **Every later rebuild rides `refresh_parsed`'s tail, not a hand-maintained list of sites.** Theme switches, width changes, big-H1 / striping toggles, media settings and arriving decodes all go through `refresh_parsed`, and `OpenSettings` / `SwitchTheme` / `CreateCustomTheme` are on the `diff_safe_action` allowlist, so several are reachable *during* a review, where a stale `parsed_new` disagrees with the row cache about block heights. `refresh_diff_parse` never calls back into `refresh_parsed` and guards on `self.diff.is_some()`.
- **The diff parse gets its own `RenderCache`** — one cache shared by two documents collides on every identical block, and per-build eviction by document membership would evict the other's entries wholesale.
- **`refresh_parsed`'s image-GC live set is the *union* of both parses.** A URL on the diff's new side but not in the editor's buffer would otherwise be evicted and immediately re-requested by the diff-side dispatch, a decode/evict loop lasting the whole review. `refresh_diff_parse` runs no GC of its own, for the mirror-image reason.
- **In diff mode `scroll` counts *diff* visual rows, so the image paths need diff-specific geometry — through one memo.** `image_dispatch::infos_in_diff_viewport_window` and `image_view::build_diff_snapshots` both read the rendered-row map via `DiffState::with_layout_index`, memoised on the layout cache and dropped with it; rebuilding per call was O(rendered rows) plus a `HashMap` allocation at frame cadence. Dispatch early-outs on an image-free new side. An image inside a *changed* region has no `ContextRendered` row, yields no snapshot and is never dispatched — it shows as `![alt](url)` source, which also keeps the media prompts honest mid-review, since a clean-region URL is by definition one the editor's document already carries. Without the dispatch, an unchanged image not yet decoded when the review opened reserves `image_max_height` blank rows for the whole review and never decodes.
- **`ROW_CACHE_CAP` is 2 because exactly two widths are queried per frame** — the scrollbar-decide width and the post-scrollbar display width. Every new per-frame `with_layout` / `with_layout_index` caller must use one of those two (the image paths use `last_doc_width`); a third turns the LRU into a full prefix-sum rebuild every frame.
- **A `ContextRendered` row carries no marker and no wash — it *is* the document.** `line_marker` returns `""`: a `- ` / `+ ` / two-space prefix would overflow table grids and code-block padding, both laid out at the full viewport width, and the markers' alignment reference is the raw context *inside* a changed region. The row cache measures it by handing the finished `Line` to `visual_rows_for_line` — the identical call `PreviewView`'s painter makes — so wrap and scroll math agree by construction; that arm sits *ahead* of the `line_text` call, which has nothing to say about a row with no source text.

### Keyboard and mouse input

- **Two-layer mouse dispatch.** `MouseDispatcher` (`src/input/mouse.rs`) is a pure state machine turning crossterm `MouseEvent`s into semantic `MouseAction`s; `mouse_ops::apply` mutates `EditorState`. Keep the split strict — coordinate translation in `mouse_ops::coord`, click counting in `MouseDispatcher`.
- **Mouse enable is gated by capabilities.** `terminal::enable_mouse()` is called from `main` only when `capabilities.mouse`, and the app gates `MouseDispatcher::dispatch` on it too, so a fake mouse event can't drive the editor.
- **Drag anchor lives in `App`, not `EditorState`** — `drag_anchor: Option<usize>` persists the mouse-down offset so the Drag handler can extend the selection. A UI-layer fact; clearing it doesn't go through the undo stack.
- **Mouse scroll uses a different bound than keyboard scroll.** `selection::scroll_by_mouse` allows `max = total - 1` and never calls `clamp_cursor_to_viewport_top`; keyboard `ScrollDown` uses `EditorState::scroll_down`, which keeps the cursor visible. Do not merge them — mouse scroll must not move the cursor. Keyboard `ScrollUp`/`ScrollDown` always step one line; `editor.mouse_scroll_lines` applies to the wheel only.
- **Click-to-offset is approximate for formatted text.** `coord::rendered_sub_line_to_offset` maps the visual column 1:1 to the raw source column — exact for unformatted lines, off by a few chars for styled spans; `RAW_REVEAL_DELAY` then turns the cursor's line raw so the user can correct on a second click. `markdown::InlineColMap` provides the exact map where precision matters (selection highlight projection in `RenderedView`).
- **A click on an already-revealed line is exact and must stay that way.** The user is looking at raw source, so `coord`'s `revealed_cursor_line` branch maps the column straight onto raw chars — which means laying the line out exactly as the painter did: `render_line` derives a *hanging indent* from the leading marker, so a revealed `- item` wraps continuations two cells in and against a narrower budget. Use `coord::revealed_raw_rows` for both the row count and the column mapping (shifting `col` by the indent on any sub-row past the first) — never bare `visual_rows_of_str`, whose indent-0 assumption drifts further with every wrap. The indent it returns is the *effective* one: when the marker is as wide as the viewport (`indent + 1 >= width`) the layout falls back to indent 0, and reporting the raw marker width there pushes continuation columns into `char_idx_at_cell_col`'s forbidden-indent zone. Any new caller of `compute_hanging_indent*` that pairs the indent with a wrap layout owes the same clamp.
- **Raw mode wraps flat — no hanging indent — and three consumers depend on that.** Raw shows the file, so indenting continuations would paint whitespace the document doesn't contain. It is also the only self-consistent choice: the scroll cache (`raw_line_at_visual_row`, `raw_total_visual_rows`, `char_offset_at_visual_row`) and the click mapping (`coord::raw_click_to_offset`) both wrap through `visual_rows_of_str`, hardcoded to indent 0. Painting through an indent-detecting helper instead put painter and scroll math in different layouts, disagreeing on the column *and* on the row count at narrow widths, so every line below painted at the wrong row. `RawView` therefore calls `line_render::render_raw_line_with_cursor`, which forces indent 0 (and thereby drops the blockquote-bar repaint, correct here because in Raw the `> ` is real source). The navigation half is mode-gated rather than forced, since `move_up_visual` / `move_down_visual` / `current_visual_col` are shared with the rendered views where the revealed line *is* indented: `hanging_indent_for_mode` returns 0 in `Mode::Raw` and detects otherwise.
- **One resolver answers "is there a link here, and which one": `mouse_ops::links::link_at_rendered_pos`.** The hand pointer (`hit_test_clickable`), the hint-line hover tooltip and the click-to-follow path all ask it, so a cell that shows a hand, names a URL and opens that URL is one decision rather than three agreeing by luck. Two things make it exact, and both were bugs first (issue: hover naming the wrong link):
  - **The position comes from `coord::rendered_click_to_line_col_on_text`**, which is scroll- *and* wrap-aware. The older walk counted one rendered line per screen row, so every wrapped line above the pointer (a long HTML block, a wrapped list item) shifted the lookup down a line and resolved the click against a different block. The `_on_text` variant additionally *declines* a cell past the row's last character instead of clamping onto it the way cursor placement does — otherwise a line ending in a link claims every blank cell to its right.
  - **Link runs are counted per *block*, not per line**: a block's N-th link-styled run pairs with the block's N-th `ui::link_view::LinkRun`, the same list `build_snapshots` pairs its own runs against. A run index taken within the clicked *line* restarts at zero on every line of a multi-line block, so every item of a link list (the generated manual index, a README's documentation list) resolved to the list's first URL.
- **The AST side of that pairing counts *runs*, not links, so an inline image gets an entry.** `Theme::image_placeholder` is the link foreground with the alt text underlined, so `[Image: alt]` is a run under *both* run-finding walks while being no link at all. `LinkRun::ImagePlaceholder` consumes the run and resolves to `None` (the raw-source scan then gets its turn); without it every link after an inline image paired with the wrong URL — `![logo](l.png) see [docs](d.md)` opened `d.md` from the image and nothing from the link, and per-block counting spread that to every later line of the block. An image *inside* a link is deliberately one run and one entry: the walk does not descend into a link's own text.
- **The two run-finding walks are not interchangeable, and neither is wrong.** `mouse_ops::links::link_run_ranges` keys on the foreground; `link_view::underlined_char_ranges` keys on `Modifier::UNDERLINED`. An in-document heading anchor carries the link color and no underline, so it is a run for the resolver and not one for the snapshots — which is why clicks resolve anchors and the (currently unread) snapshots do not. Both consume one `LinkRun` per run they find, so each stays internally aligned; a change to either predicate has to be argued against both.
- **`is_link_style` keys on the link *foreground*, not on `Modifier::UNDERLINED`.** The underline is how links are decorated but it is not theirs alone — the default theme underlines H2–H6 — so the marker test classified every heading as a link, and the run coalescing then swallowed a real link written inside one. Every theme paints link text in the link color inside a heading and a blockquote alike (`link_text` / `link_file`, and the deliberately underline-free `link_heading` for an in-document anchor), which makes the color the honest signal. It is only a *candidate* test: an unrelated slot may share the color (`syntax_function` is derived from it) and a colorless theme (`Monochrome Dark`) has nothing but the underline, so the AST pairing above is what turns a candidate into an answer.
- **The resolver runs at pointer-report cadence, so it owes three economies.** It is asked on every `Moved` event, and the naive shape paid a document-sized cost per pointer report. (1) `hit_test_clickable` is split: `App::dispatch_mouse_event` resolves the hovered link for the hint line and then composes `hit_test_clickable_non_link` with its own `hovered_link` — the full `hit_test_clickable` remains the whole answer for tests and any other caller, but the app must not ask it to resolve a link it just resolved. The substitution is exact only because both reads use the same position *and* the same viewport width. (2) `rendered_click_to_line_col_on_text` gets the `LineLayout` (row table, hanging indent, char count) back from the call it inverts, rather than rebuilding the char vector and wrap table from `state`. (3) The block source comes from `Buffer::byte_slice_to_string`, not `Buffer::contents()` — slicing one block out of a materialized document is O(document) per hover. The remaining `contents()` in `hit_test_clickable_non_link`'s checkbox / footnote arm is the same cost and still unpaid; `footnotes::footnote_at_offset` and `list_edit::find_list_at` want whole-source byte offsets.
- **`links::link_at_offset` is the raw-source fallback, not the primary path.** It scans a line's bytes for a balanced `[...](...)`, so it catches a click on the revealed `[text](url)` source of the cursor's block and in Raw mode; it sees no reference-style links or autolinks, and it is consulted only after `link_at_rendered_pos` declines.
- **Checkbox toggling short-circuits cursor placement.** `checkbox::toggle_checkbox_at` runs BEFORE `click_to_char_offset` in the `Click` arm: a click on the `[ ]` glyph toggles and returns without moving the cursor; clicks elsewhere on the line fall through.
- **A table drag resolves its target on one axis, geometrically — never by asking `hit_test` for a classification.** `col_ranges` / `row_ranges` cover only *content*; the `│` borders, `┬` vertices and `├─┼─┤` separators sit in one-cell gaps that `hit_test` answers with `ColumnBorder` or nothing, so a row drag asking it for `RowHandle | Cell` stalled its hover wherever the pointer crossed a border. `data_row_at_y` / `column_at_x` snap to the nearest row / column within the table's extent instead: a row drag follows the pointer's **y** alone, a column drag its **x** alone. They also back the two grab hit-tests, so the whole gutter height and top border are live. Outside the extent both return `None` — the hover freezes rather than snapping to an edge.
- **A handle acts only on the focused table, because that is the only table it is drawn on.** `paint_handles` draws `⠿` / `⇔` / `✕` only on the table the cursor is inside, while `hit_test` runs against every visible snapshot — so `dispatch_table_click` routes *every* handle hit through `focus_table_first`, which moves the cursor into that table and consumes the click without acting. Otherwise a press drives a control that was never painted (a click on another table's right border deletes a row from it). Only `Cell` and the inert leftmost outer border are exempt, falling through to ordinary cursor placement.
- **The `✕` pair is scoped tighter, spatially and temporally.** The column-delete hitbox is `column_glyph_x` ±1, not the column's full width, so a click aimed at a border from the bottom row resizes rather than dropping a column (`column_glyph_x` is shared with `paint_handles`). `TABLE_DELETE_COOLDOWN` (250 ms) swallows a second delete landing too soon, so a habitual double-click removes one row. **The cooldown is anchored to the delete, not to the click chord** — as a chord gate it never expired, since `MULTI_CLICK_WINDOW` restarts on every press, so clicking `✕` faster than 2.5 Hz deleted exactly one row and then went dead. `EditorState::last_table_delete_at` is stamped by `table_drag`'s two delete helpers, only on a delete that applied.
- **Multi-click arms must dispatch table hits too, because a drag *is* a click-chord member otherwise.** `dispatch_table_click` is shared by the `Click` / `DoubleClick` / `TripleClick` arms, which behave identically: a table interaction is a gesture users retry, and the second press arrives as `DoubleClick`. `MouseDispatcher::dragged_since_down` closes the other half — a press that turned into a drag doesn't start a chord, so the retry is a fresh `Click`. Both halves are needed; the flag can't help a retry whose *first* press never dragged.

### Unified UI controls

Interactive elements inside modals/overlays are one family, defined in `ui::controls`. The governing rule: **a control resolves its own styling from `controls`; the parent container only reports whether it is `focused` / `disabled`.** Never hand-roll a focus style in a modal.

- **Four flavors, declared at the definition site.** **Toggle** (`toggle_spans`) — an on/off slider, and the one control whose *widget* keeps its value color when focused (inverting it would destroy the on-is-green reading), so focus shows only in the label column. **Pill** (`pill_spans` over a `&[&str]`, e.g. the shared `ASK_ALWAYS_NEVER`) — a multi-value `‹ value ›` selector cycled with ←/→; on/off is **not** a pill flavor, a binary setting uses the Toggle, and a row declares which via the `Control` enum (don't reintroduce `PillStyle::Toggle`). **Text input** — `controls::text_value_style`, with the blink-stable cursor from `ui::cursor::text_field_spans`. **Button** — `ui::button_row`, styled by `controls::button_style`.
- **Focus is one language; the label column is the single source of truth.** `REVERSED` means "filled affordance". `controls::focused_style` (= `theme.modal_button_focused`) is the shared focus fill, and `controls::control_label_style(focused, disabled, theme)` resolves a labeled row's label column — focused → `modal_item_selected`, disabled → `modal_close_hint`, resting → `modal_item` — called by **both** the settings overlay and the welcome modal. A focused row is one unit: pad the label across the whole column so the fill spans label → widget.
- **Buttons go through `ui::button_row`, never a hand-built literal.** Construct a `Button::bracketed(label)` and let `render_button_row` (centered footer) or `render_button_at` (left-aligned inline) add the `[ … ]`, size it, place it and return the hit-rect.
- **Cycle + cascade logic is shared too.** Pill / toggle inputs route through `controls::Control::apply`, whose pill arm and every index-valued caller delegate wrap-around to `controls::cycle_index`; `controls::apply_images_cascade` (images-`Never` forces remote-`Never`, stashing/restoring the prior choice) is shared by the settings overlay and the welcome modal.

### Modals, overlays, and the keybinds editor

- **Live `KeyMap` on `App`, draft inside the overlay.** `App::keymap` is built once in `run()` and held for the process's life. The keybinds overlay opens with a *clone* (`KeybindsState::draft_keymap`) plus a cloned `KeyBindingOverrides`, and every rebind mutates only the draft; nothing reaches `App::keymap` / `App::keybindings` or `keybindings.toml` until `[ Save ]` returns `KeybindsResponse::Save { keymap, overrides }`, and Esc / `[ Cancel ]` discard it. Don't regress to mutating the live keymap per keystroke — a fumbled chord would then only be recoverable by hand-editing `keybindings.toml`.
- **Combined view+edit keybindings overlay.** `OpenKeybinds` owns it; there is no separate cheat-sheet variant, and a user binding to the removed `Action::ShowCheatSheet` fails parsing with `KeyMapError::UnknownAction`.
- **A footer wraps; it never clips.** A clipped button is still focusable and still carries a click rect pointing off the frame — the one outcome that lies. `button_row::button_rows` packs at the width it is given; `render_buttons` paints a row per group, separated by a blank (`ROW_SPACING`), since rows stacked tight read as a list rather than as alternatives — so `button_rows_height` reports the *painted* height, not the row count. Both consumers must ask it at the width the render packs against: `ModalView` sizes `pinned_bottom` from the prospective inner width both already agree on, and a bespoke overlay asks `button_row::footer_row_count` and gives the button rect *all* the rows left below it — a flat `height: 1` paints only the first row, leaving a wrapped button unpainted while Tab still focuses it. That is every multi-button overlay (search, save-copy, insert-table, keybinds); a **single**-button footer (diff intro, export theme, welcome) always gets exactly one row and is deliberately left alone. `footer_row_count` runs the real sizing arithmetic — `modal_dimensions_for`'s clamp, then `compute_pad_h`, with the caller's own `max_pad_h` (the keybinds overlay raises it to 8) — because a flat `MIN_PAD_H` subtraction overestimates the inner width by up to `2 * (max_pad_h - MIN_PAD_H)` and reserves one row for a footer that wraps onto two. `render_buttons` returns a rect per button whatever fits: callers index the result by button.
- **A body narrower than the modal is centred as a block.** The footer is often the widest thing in a modal, and left-aligning the body inside the width it bought pushes a self-centred page (About's art and title column) off-centre by half the difference. `ModalView` renders *and measures* the body in a `body_render_w`-wide sub-rect: text stays left-aligned *within* the block, only the block moves.
- **A body that has to know its own width gets it from `modal::chrome::body_columns`** — the terminal less `MIN_PAD_H` a side, the widest body `ModalView` can hand back. The two modals needing it both have a *picture* for part of their body, and both therefore rebuild it each frame; neither may cache it. The About page drops its pod below that width — one ASCII block, so a wrap shears it rather than shortening it — while everything else centres in a narrower column, the version row falls back to the bare `v0.1.1`, and each rotation is padded to the row count the *longest* tagline needs at that wrap width (a fixed two resized the frame mid-rotation once the wrap tightened). The cheat sheet caps its code-block and block-quote washes there, and only those: a wash is a rectangle standing in for a block, so a wrapped one repeats its surface on a second ragged row, while every other row is content and must wrap like any modal body — clipping the whole body instead truncated the syntax examples the sheet exists to show. The cap is `EXAMPLE_INDENT` short of the body width, because that is where the wash *starts*: flush to the right edge it has a margin down one side and none down the other, which reads as crowding the frame whatever padding the modal has.
- **`ModalView` is scrollable; the bespoke overlays are not.** `ModalState` carries `scroll`, `last_total`, `last_visible`, `scroll_by(i32)`. Up / Down / PgUp / PgDn / Home / End route to scroll, never to button focus — Left / Right and Tab / Shift-Tab still cycle buttons. Wheel events reach open `ModalView` slots via `modal_wheel_delta`. The palette / settings / keybinds overlays don't scroll because their bodies fit.
- **Bracketed paste routes to the top modal's focused field.** With a modal open, `dispatch_modal_event` forwards `Event::Paste` to `Modal::handle_paste` (pop-dispatch-push, like `handle_wheel`/`handle_click`); otherwise it goes to the buffer via `dispatch_paste`. The trait default is a no-op, so button-only modals ignore pastes. Every text-input modal's `paste()` runs the payload through `ui::sanitize_paste` first — one source of truth that strips control chars (a multi-line clipboard collapses to one line) and caps at `PASTE_CHAR_CAP` (1024) — then layers field-specific policy and *mirrors that field's keyboard `Char` arm exactly* (append vs. cursor-insert, focus gating, digits-only, live preview). The search modal is the one field that transforms *before* sanitizing (`search::escape::escape`). Don't flatten in the editor path: `dispatch_paste` keeps newlines because the buffer is multi-line. A new text-input modal must override `handle_paste`.
- **External-editor flow needs three things, in order.** Before `Command::new($EDITOR).status()`: (1) pause the crossterm read thread, (2) drain the rx channel, (3) suspend the terminal. Skip any and the editor races our read thread for stdin — bytes get split, keystrokes lag, and OSC responses to startup-time queries leak into the buffer. The read thread is poll-based (`event::poll(100ms)`) precisely so a `read_paused: Arc<AtomicBool>` can stop it without interrupting a blocked `read()`. Afterwards `terminal::re_enter(mouse, keyboard_enhancement)` reinstates alt-screen + raw mode + transient features and `Config::load()` re-runs. See `src/app/external_editor.rs`.
- **`Modal::kind` and `Modal::dismissable` are stored as struct fields, not hard-coded.** Every `ModalView` modal sets `kind: ModalKind` and `dismissable: bool` once in `new()`/`from_*()`, and all three read sites — the `ModalView::new(..)` call, the `state.handle_key(..)` call, and the trait methods — read those fields. Do NOT pass literals at any of them; they will drift. `dismissable` controls three things together: the rendered `esc` close-hint, the cached `esc_button_rect` for click hit-testing, and whether `Esc`/`n`/`N` fire `ModalResponse::Cancelled`. Modals not using `ModalView` (palette, settings, keybinds, save_copy, insert_table, theme_picker, export_theme) inherit the trait defaults (`Normal` / `true`); don't add no-op overrides.
- **The welcome modal is dismissable only when it wasn't a first run.** Same field-not-literal rule: `WelcomeState::dismissable` is read by the `Esc` arm, by `show_close_hint` in `render` (which populates `esc_button_rect`, so the click path needs no second gate), and by `Modal::dismissable`. `WelcomeModal::from_state` (first run) leaves it `false` — Cancel is replaced by an explicit "Show on next launch" toggle, and there is no prior choice to protect. Every on-demand opening (`Action::OpenWelcome`, the capabilities notice's "Adjust settings") goes through `WelcomeModal::new` + `with_dismissable(true)`, because reopening carries a risk the first run doesn't: below truecolor `WelcomeState::new` force-sets images and diagrams to `Never` and `save_outcome` *persists* that, so without a write-nothing exit, merely looking at the surface from a weaker terminal overwrites settings chosen on a capable one. `WelcomeResponse::Cancel` → a plain `ModalOutcome::Close`, with deliberately no fingerprint seeding.
- **Construct `ModalView` via `ModalView::new(...)`, not a struct literal** — the constructor pre-fills `max_pad_h` to `MAX_PAD_H` (4); chain `.with_max_pad_h(n)` to override.
- **A prose modal must cap its content width; a tabular one must not.** `ModalView` sizes itself to its longest *unwrapped* body line — right for tables (capability rows, keybindings), wrong for prose, where a wrapped paragraph's natural width is the whole sentence. Chain `.with_max_content_width(PROSE_CONTENT_WIDTH)`, a count of *text* columns, so the modal is that plus `2 * max_pad_h`; it matches the welcome modal's `CONTENT_WIDTH` so both prose surfaces read at the same measure, and is raised to the button-row width before clamping so it can't clip the footer. Don't pre-wrap prose into short `Line`s — `ModalView` wraps and sizes with `wrapped_rows`, so hand-splitting double-wraps at narrow widths.
- **Horizontal padding lives on `ContentSize`, not on `FrameOpts`.** `FrameOpts.content` embeds the same `ContentSize` fed to `centered_rect_for_content`, so the sizing pass and `draw_frame`'s padding can't disagree: set `max_pad_h` once (or take `MAX_PAD_H` via `..Default::default()`) and pass that one value to both. Do NOT reintroduce a parallel `FrameOpts.max_pad_h`. The keybinds overlay raises it to 8 so the "Already bound to …" string can't reflow its dense table during capture.
- **Preview-mode Ctrl-key allowlist.** `input::mode_handler::default::preview_safe_action` decides which Ctrl-* chords fire in Preview. Read-only overlay openers (`ShowCommandPalette`, `OpenSettings`, `OpenWelcome`, `OpenKeybinds`, `OpenConfigFolder`, `ShowMarkdownCheatSheet`, `SwitchTheme`, `CreateCustomTheme`) belong on it — a new modal-opening action must be added, or the chord silently no-ops in Preview.
- **Focus vs. persistent selection (styling convention).** When a modal carries a *persistent selection* independent of focus — e.g. the export-theme modal's highlighted theme name — use three tiers: focused → `theme.modal_button_focused` (filled, strongest); selected but unfocused → `theme.modal_item_selected_unfocused` (`secondary` **fg** on `surface_elevated`, outlined); neither → `theme.modal_item`. Don't reuse `modal_item_selected` for the middle tier — it is also a filled `primary` bg and collides with the focused affordance. For composite affordances (checkbox glyph + label), apply the unfocused-selection style to the *glyph only*. Ordinary labeled control rows are *not* this case; their focus styling is `controls::control_label_style`. See [`docs/dev/theming.md`](docs/dev/theming.md) §"Focus vs. persistent selection".

### Update check

- **One fetch, one cache, four states, three entry points.** `App::latest_release` is the session cache every path reads; `ReleaseStatus` is `Pending | UpToDate | Available | Failed`, and `UpdateModal` renders all four. The startup check pushes it *only* for `Available`; the About page's `[ Check for updates ]` and `Action::CheckForUpdates` push it in whatever state is known and let the in-flight result replace it. Keeping the up-to-date and failure states on the same modal is what lets an explicit check answer honestly while the startup path stays silent — don't split them.
- **Both conclusive states share one body shape and one title:** a verdict line, a blank, then `Installed version:` / `Latest release:` rows — a two-row table with padded values, not numbers embedded in a sentence, so the states differ by verdict rather than layout. The frame is captioned `Check for updates` in every state, `Available` included. `Available` alone adds the notes and `[ View on GitHub ]`, which opens *that release's* page (`release_url`), not the releases list.
- **The up-to-date / available split is decided once, in `ReleaseStatus::from_fetch`, not at render time** — the modal picks copy from the variant and `policy::notice_due` gates the nag on it, so both consumers must agree. A build *ahead* of the latest release compares `Less` and is not an update.
- **A comparison that can't be made is its own state.** `compare_versions` answers `Option<Ordering>`; `None` (either side unparseable as a dotted numeric version — `v0.2.0-rc1`, `v0.2.0+build.7`) becomes `Inconclusive`, which `notice_due` keeps as silent as `UpToDate`. Don't fold it back in: both are silent on the notice path, but only one is *true*, and the explicit-check modal prints installed and latest versions right under its verdict. `Inconclusive` says "Couldn't compare versions." and keeps `[ View on GitHub ]`. `ReleaseStatus::tag()` is the single accessor across the three states that name a tag.
- **The notice cannot join `App::new`'s startup-modal ordering** — every other startup modal is built synchronously in a deliberate priority order; this one depends on a result arriving much later. A finding parks in `App::pending_update_notice` and `tick_update_notice` pushes it on the first frame `modal_stack.is_empty()`. Gate on *the stack being empty*, never on "no welcome modal" — that is what keeps it robust against the first-run welcome, the config warning, the capabilities notice, and anything added later.
- **The startup check waits out the first-run welcome modal**, which is where `check_for_updates` is asked — a check fired before it makes the request the setting exists to gate. `spawn_startup_update_check` is therefore a `tick_timers` member, not a one-shot call from `run()`: it parks while a `WelcomeModal` is on the stack and re-reads the setting *after* it closes, so a first-run decline is honored on that same launch. Only the welcome gates it — the config warning and capabilities notice are not consent surfaces for this.
- **Both field scans are anchored to real top-level keys.** `parse::top_level_value` tracks object depth and consumes strings whole; a bare `find("\"body\"")` matches key text inside another field's *value*, and a release `name` is free text somebody types. Depth also excludes the nested `author` / `assets` objects. Still not a JSON parser — it locates one key and hands the rest to the caller.
- **`tag_name` is validated, not just extracted.** It is remote text reaching a rendered line *and*, via `fetch::release_url`, a URL handed to the system browser — so `parse_tag_name` refuses a tag over `MAX_TAG_BYTES` (64) or carrying anything outside the semver alphabet (`is_tag_char`: ASCII alphanumerics plus `.`, `-`, `_`, `+`). It rejects rather than sanitizes, and a rejected tag drops the whole release (`parse_release` → `None`) — notes without a version are not a finding. The excluded characters are the ones that would break the `Latest release:` row's layout (whitespace, controls) or change what the URL resolves to (`/ ? # % &`).
- **`sanitize_notes` strips `Cf` formatting characters as well as controls** — bidi overrides and zero-width joiners are not `char::is_control`, and they are the last thing remote text could do to a surface that never re-parses it as Markdown.
- **`last_update_check` is stamped at *spawn*, not on arrival** — a worker that hangs to its timeout, or a process killed before the result lands, would otherwise leave the clock untouched and re-check every launch. The cost is that a transient failure waits out the full interval, which is right for a notification nobody is waiting on.
- **The throttle governs the automatic check only.** `open_update_modal` always re-fetches: the 24 h gate bounds *unattended* chatter, and an explicit request is the opposite. It shows a cached *positive* result meanwhile so the modal isn't blank, but never a cached `Failed`.
- **Bookkeeping writes must not flash.** `update_notified_for` and `last_update_check` go through a bare `Config::save`, not `save_config_with_flash` — the user changed no setting. `Config::save` already declines to write under `--no-config`, so neither needs its own gate.
- **Notes get structural styling, never Markdown parsing.** `ui::update_check::note_lines` bolds an ATX heading (dropping its `#` run), swaps a `-`/`*`/`+` marker for a `•`, and drops the blank line Keep a Changelog puts *under* each heading while keeping the one above. That is the whole vocabulary: a *line* classified locally over already-bounded text, choosing between three fixed styles. Don't grow it into an inline parser — `**bold**` and `[text](url)` stay literal on purpose, and a parser would hand a release body emphasis, links, images and layout inside an app modal. Wrapped lines have no hanging indent; `ModalView` owns the wrapping.
- **Release notes are remote text and are bounded on the worker, before anything else sees them.** `sanitize_notes` cuts at cargo-dist's first `## Install` heading, strips control characters, and caps at 30 lines / 2 000 bytes, so the main thread never holds an unbounded string. They are rendered a line at a time with structural styling only and **never re-parsed as Markdown**.
- **`body` needs a real JSON string decoder; `tag_name` does not.** A tag never contains a quote or backslash, so `parse_tag_name` scans to the next `"`. The body is prose carrying quotes, backslashes, newlines and emoji, so `decode_json_string` walks escapes properly — an embedded `\"` would otherwise terminate the value at the first quotation mark the author typed. Still no `serde_json`: this is a JSON *string-literal* decoder, and every failure degrades to "no notes". (A `"###` sequence terminates an `r#"…"#` literal, so fixtures containing one need different quoting.)
- **The release notes ship from `CHANGELOG.md`.** `dist` reads the section matching the tag into the top of the GitHub release body, which edamame reads back and shows above `## Install` — so a `CHANGELOG.md` entry *is* what users read in the update modal. A release cut without a matching section still notifies, just with no summary.
- **`ui::update_check` takes plain values, not `ReleaseStatus`.** Nothing under `src/ui/` imports `crate::app`, and this is not the module to start: the modal adapter maps the status onto `ui`'s own `UpdateReport`. That translation is the only reason `update_check` can stay under `app` rather than becoming a leaf subsystem.
- **Every About-page button has a named index arm.** `AboutModal::resolve` matches `RELEASE_NOTES_BUTTON` / `CHECK_UPDATES_BUTTON` / `VIEW_ON_GITHUB_BUTTON`, and its final `ButtonPressed(_)` arm does *nothing*. It was a catch-all opening GitHub, so a newly added button silently opened GitHub instead of doing its own job — exactly what `[ Release notes ]` would have done.
- **The About page reports no release information at all.** It used to fetch on every first open, which made merely opening the page a network request and put a second surface in the business of rendering release state.

### Post-upgrade notice

- **A second, unrelated notion of "new".** `update_check` asks whether a newer release exists on GitHub; `app::post_upgrade` asks whether *this build* is newer than the one that last ran, and answers from the `CHANGELOG.md` compiled into the binary. No network, no consent setting, no throttle — so `ReleaseStatus` gains no variant, since every state it has names the outcome of a fetch. The two share `parse::sanitize_notes` and `ui::update_check`'s renderer, so a changelog entry and a release body reach the screen in one vocabulary with one set of caps.
- **Synchronous, not park-and-tick.** `update_notice` parks its finding for `tick_timers` only because a network result lands long after `App::new` has fixed the startup modal ordering. Config, changelog and `CARGO_PKG_VERSION` are all in hand in the constructor, so this modal joins that ordering directly — one slot below the welcome — with no `App` field, no per-frame poll and no "wait for the welcome" carve-out.
- **The decision belongs to `App::new`; the write does not.** `test_utils::make_app` builds an `App` through `App::new` and most callers hold no `config_isolation()` guard, so a `Config::save` there would rewrite *the developer's own* `config.toml` on every `cargo test` run. `App::stamp_last_version_seen` therefore runs from `App::run`. Deciding is exempt because `config_writes_allowed()` is an atomic load, not I/O. A new startup modal recording that it fired owes the same split.
- **An empty `last_version_seen` means "no version recorded", and `show_welcome` is the tell.** The empty string is what a fresh install has *and* what an upgrade from a build predating the field has; guessing wrong either greets a brand-new user with notes for a version they never ran, or eats the first notice for every existing user. Only a returning user could have turned `show_welcome` off. Once a real version is recorded every later upgrade takes the non-empty branch, so there is no migration path to delete later.
- **The stamp is unconditional on whether anything was shown, and `--no-config` refuses the notice outright.** A release with no matching changelog section is silent, but still records the version — otherwise "nothing to say" would be re-evaluated forever. Under `--no-config` the stamp cannot persist, so the notice is gated at the decision (`config_writes_allowed()`) rather than left to `Config::save`'s own refusal: shown anyway, a one-time notice becomes an every-launch one.
- **One body, two entry points, differing only in the opening line.** `PostUpgradeOccasion::Upgrade` opens on `Updated to vX.` with no version row (the headline names the number); `OnDemand` — the About page's `[ Release notes ]` button — opens on an `edamame version: vX` row with no headline, because a verdict line there would claim an upgrade that never happened. `PostUpgradeModal` carries the occasion, since `render` is where the two paths meet again. The on-demand path also *always* answers, rendering `PostUpgradeReport::NotFound` for a version with no section, and reads and writes no bookkeeping — looking is not being notified. `Some(vec![])` (an empty section) and `None` (no section) must stay distinct, or that modal reports an absence about a release that was merely quiet.
- **The section terminator includes a link-reference definition, not just the next `## `.** The last section in a Keep a Changelog file is followed only by the `[0.1.0]: https://…` block, so without that arm the oldest release's notes end in raw URLs — visible only on the launch where that release is installed, which is the one nobody tests. A `### Added` subheading is deliberately not a terminator (third character `#`, not a space), or every entry would stop at the blank line under its own heading. Versions match on the bracketed text exactly, so `0.1.2` cannot claim `## [0.1.20]`.
- **A test building an `App` with `show_welcome = false` must record a version too.** With an empty `last_version_seen` that is exactly the "upgraded from a pre-field build" case, so the notice lands on the stack and breaks every assertion about what is on top. `test_utils::app_with_welcome` and `nav`'s builder both stamp `INSTALLED_VERSION`.

### Images, diagrams, and export

- **The accepted image-format list is a security boundary, and Cargo feature unification is what breaks it.** `Cargo.toml` declares `image` with exactly the formats edamame accepts (`png`, `jpeg`, `gif`, `bmp`, `webp`; SVG goes through `usvg`), and `loader::decode` refuses anything else as an ordinary `Unsupported` error. That list only holds if *no other crate in the graph* asks `image` for more, because Cargo unions features graph-wide: `ratatui-image`'s `image-defaults` feature forwards `image`'s full defaults, silently re-widening the decode surface (and dragging in the AVIF *encoder* for a program that encodes nothing). So `ratatui-image` is declared `default-features = false, features = ["crossterm"]`, and a new dependency wanting `image` must be checked the same way: `cargo tree -e features -i image`. Widening the list is a deliberate decision recorded in `docs/editing.md`, never a side effect.
- **Advisory policy is a checked-in file, not CI flags.** `.cargo/audit.toml` denies informational advisories (unmaintained / unsound / yanked) alongside vulnerabilities and carries the reasoned `ignore` list, so `cargo audit` from the repo root gives the same verdict as CI. An advisory belongs in `ignore` only when the fix is genuinely unreachable (upstream pin, or our own deliberate `=` pin); each entry records why it is acceptable and what would let us delete it. If a bump can clear it, take the bump.
- **The media prompts are per *document*, not per launch — and one method owns that.** Under the default `images.enabled = "ask"` (and its diagrams / remote twins) the prompt is the *only* thing that sets `session_images_enabled`, and `effective_images_enabled` is false until it does, so a question never asked means images never decode. All three prompts are built from the open document (`Ask` **and** this document has an image / diagram / remote URL), so every path replacing the document's *contents* must re-evaluate them. That is `App::on_document_contents_swapped` (marks `images_dirty`, queues the three), called by `load_file_into_editor`, `reload_buffer_from_disk` and `apply_diff_resolution` — the last being the *default* external-change path, since a clean buffer with `diff_on_change` goes to diff review rather than a reload (issue #30). One method rather than three copies, because the copies are how the diff path was missed. A new contents-replacing path owes the call, placed **after** `refresh_parsed`, since the prompts read `editor.parsed`.
  - Each `queue_*_prompt` helper carries its own gates, so every queue site — the document swap and the three settings-overlay `apply_*` handlers — inherits them: `media_renderable()` (below truecolor nothing is asked, since `Always` / `Never` would persist a choice made where the result can't be seen), an answer already given this session, and a prompt already on the stack (idempotent). The session-answer gate is what forces `session_remote_declined` to exist: images and diagrams record a decline in their `Option<bool>` by construction, while `session_allow_remote` is a bare bool, so without a companion flag a dismissed remote prompt is indistinguishable from "never asked". The two remote flags are mutually exclusive (the `Yes` / `Always` arms clear the decline), and a persisted policy change supersedes both (`apply_remote_policy_change`).
- **A new document means a new `EditorState`, and everything App-level it needs must be re-applied — `app::configure_new_editor` is where that lives.** `load_file_into_editor` builds a whole new `EditorState` (and `ImageCache`) per document, so anything wired onto the startup editor in `App::new` or `spawn_event_threads` is *gone* for every file opened by link, back-navigation or `$EDITOR` return. It has drifted twice, both invisible until a second document was opened: the encoder worker's `ResizeRequest` sender (attached once in `spawn_event_threads`; without one `get_protocol_pair` returns `None` and `paint_images` draws the `[Image: alt]` placeholder while the images cache perfectly in the background — `App::resize_tx` keeps the clone the swap site re-attaches), and `cursor_blink` (applied only in `App::new`, so `cursor_blink = false` started blinking again after the first link follow). A new setting an `EditorState` reads out of `Config` belongs in `configure_new_editor`; the `resize_tx` re-attach stays separate only because `App::new` has no sender yet when it builds its editor.
- **Decode happens off the UI thread.** `image::loader` runs in a worker; results arrive as `AppEvent::ImageReady`. URL fetches use `ureq` (rustls, no system OpenSSL). Failures are memoised so a reparse won't re-issue a doomed request every frame.
- **ratatui-image encode uses a second worker.** `ResizeRequest` / `ResizeResponse` route through `AppEvent::ProtocolReady` and a pending-request FIFO; failures still pop the queue so a placeholder stays visible until a later frame re-enqueues. `ThreadProtocol::resize_encode` *moves* the inner `StatefulProtocol` to the worker, so `render()` draws nothing until the response lands — and `ProtocolPair::native_ready` latches on the first successful encode and is never cleared. `paint_native` must therefore gate the native render on `native.protocol_type().is_some()` as well as `native_ready`, falling back to the scratch otherwise; gating on `native_ready` alone leaves a hole where `clear_visible_reserved_rect` just blanked the rect.
- **A native transmission that is still on screen must not be re-sent.** iTerm2 and Sixel deliver the full raw png on every render — `Iterm2::render` puts the whole base64 payload in one cell's `symbol` — and `Buffer::diff` sets `invalidated = max(symbol.width(), invalidated) - 1` per cell, where that symbol's display width is the payload length. `invalidated` therefore stays positive for the rest of the buffer and **every** later cell is re-emitted, including a second image's payload cell: one image at the top of a document retransmits every image below it on every frame, which at the cursor-blink cadence reads as a ~2 Hz flicker. Kitty is immune (transmit once, paint cheap placeholder rows), hence the symptom being iTerm2-only.
  - `paint_native` records each transmission as an `image::cache::NativePaint { rect, generation, frame }` and, when the *immediately preceding* frame left that same encoding at that same rect, marks the whole rect `skip` so ratatui emits nothing. Two things keep the record honest: the one-frame adjacency rule (any scratch / suppressed / off-screen frame invalidates it — the scratch paths clear it explicitly, the others rely on the frame gap, pinned by `a_suppressed_frame_forces_the_next_native_frame_to_retransmit`), and `ImageCache::invalidate_native_paints()` on the two events that repaint the screen behind our back: `App::on_resize` and the `terminal.clear()` after the external editor returns. `ProtocolPair::native_generation` rides along as defense in depth only.
  - **The skip marking makes the frame buffer lie** — it records blanks over rows still showing an image — and what keeps that from stranding a ghost is that ratatui's `impl PartialEq for Cell` compares the `skip` flag alongside symbol and style, so the first frame that stops skipping diffs unequal and emits the blanks. Without it, an image scrolling away into empty space would never be erased (`skipped_rect_still_diffs_against_the_same_cells_unskipped`). The frame counter is bumped in `App::draw_frame`, **not** `paint_images`: Raw and Diff draw frames without painting images, and counting only painted frames would make a pre-Raw transmission look adjacent to the first frame back in Rendered. A new path that repaints the terminal outside the paint pass must call `invalidate_native_paints`.
- **`Capabilities::halfblocks_picker` must be forced to `ProtocolType::Halfblocks`.** Both ratatui-image constructors are wrong: `Picker::halfblocks()` hardcodes `font_size` to (10, 20), so an image changes aspect ratio whenever it crosses the native↔halfblocks boundary; `Picker::from_fontsize()` keeps the probed size but *infers a protocol from the environment*, returning an **iTerm2** picker whenever `$TERM_PROGRAM`/`$LC_TERMINAL` names iTerm2, WezTerm, VS Code, Warp, Hyper, Tabby, rio or mintty (or tmux under one of those). `terminal::capabilities::halfblocks_from` takes the font size from the first and stamps the protocol from the second; `image::render_halfblocks_scratch` re-forces it locally. Getting this wrong is catastrophic and silent: the scratch then holds one cell carrying a whole base64-PNG escape surrounded by `skip` cells, which `paint_halfblocks_partial` cannot clip by row — the image flashes only on frames where row 0 is copied, re-transmits on every scroll frame, and punches through the modal dim sweep.
- **iTerm2 answers the Kitty capability query but can't do unicode placeholders.** ratatui-image's Kitty backend renders *exclusively* through that extension, and iTerm2 3.5+ implements the graphics protocol without it — so the probe lands on `Kitty`, the image is transmitted, never placed, and the reserved rows stay blank. `detect_image_protocol` overrides `Kitty` → `Iterm2` when `iterm2_hint_is_trustworthy()`, factored into the pure `resolve_protocol(probed, iterm2)` so it is testable without live probing; only `Kitty` is overridden. **The override is suppressed inside tmux**, because the env hint it rests on is exactly what tmux makes stale (`TERM_PROGRAM` / `LC_TERMINAL` are not in tmux's default `update-environment`, so a session created from iTerm2 and reattached from Ghostty still advertises iTerm2), while the stdio probe asks the live terminal through passthrough. The case this gives up — tmux inside iTerm2 — falls back to blank image rows, the pre-override status quo and recoverable via halfblocks, unlike a wrong-protocol pin on Ghostty.
- **Mermaid diagrams use synthetic cache keys.** `diagram::mermaid` renders Mermaid → SVG → PNG via `mermaid-rs-renderer` + `resvg`/`usvg`, keyed `diagram-mermaid-<sha256>` so a rendered diagram survives reparses. Pin `mermaid-rs-renderer` exactly (`=0.2.2`) — pre-1.0, known panic bugs, rapid churn; `resvg`/`usvg` versions must match what it transitively depends on so cargo doesn't compile two copies.
- **A revealed image block reserves one row per *source* line, not its image's rows.** A `Block::ImageBlock` reserves as many rows as the decoded image occupies, which has nothing to do with how many lines its source was written on — so the raw-source reveal was clipped by a short-wide diagram (issue #24), padded out by a tall one, and a one-line `![alt](url)` left floating in a screenful of blanks. **Both are the same bug and take the same fix; the gate is `is_image_block`, not `is_mermaid_block`.** `EditorState::image_reveal` stashes an `ImageReveal { ordinal, url, rows }` for the block the cursor rests in, and `refresh_parsed`'s row-override consults it **first** — ahead of both the decode cache and the images-disabled collapse to 1 row — so the document reflows.
  - The transition is resolved once per frame by `sync_image_reveal` from `App::prepare_viewport`, because the reveal is time-driven and `RAW_REVEAL_DELAY` elapses with no event of its own; the call is a no-op when the target hasn't moved. **A sync returning `true` owes `ensure_cursor_visible`**: the reflow moves rendered rows under a cursor that never moved, and `ensure_cursor_visible` otherwise runs only off a motion or an edit — so entering a fence from below near the fold grows the block and carries the cursor off screen, while the image direction shrinks it and can strand the cursor above `scroll` (`revealing_a_diagram_at_the_fold_keeps_the_cursor_on_screen`). The `dims` given to that call were measured *before* the reflow, so a reveal changing the line count can paint one frame with a stale gutter width; the `needs_draw` it sets re-measures next frame. It holds the current reservation while `parsed_dirty`, since a diagram's synthetic URL hashes its source and an ordinary image's *is* source text, so mid-typing the parse names a URL the next reparse retires — and an in-line edit can't change the line count anyway.
  - **The row count is `rendered_view::revealed_source_line_count`, not the raw line count**, because a block's *extended* byte range absorbs the blank line following a paragraph — and the promoted `![alt](url)` paragraph with it — while a fence's range stops at its closing ```. That blank is a virtual block with a rendered row of its own, so counting it reserves one row too many. It otherwise counts through the same split the reveal paints with (`raw_source_lines`), so reserved rows and painted lines can't disagree.
  - **The block is named by ordinal *and* URL, and `ImageRowOverride` takes both** — a URL alone doesn't identify a block, so a document using one image twice would see every copy collapse to the revealed block's line count (`revealing_one_image_leaves_a_duplicate_of_it_alone`). The ordinal counts `Block::ImageBlock`s in document order (`Renderer::image_block_seq` and the index into `ParsedDoc::image_blocks`, both walking the same top-level list). The URL is a staleness check for the `parsed_dirty` hold: a reservation whose block has stopped being an image matches nothing, instead of the ordinal sliding onto the next image. `sub_lines_in_block`'s mermaid branch clamps to `block_own - 1`, which is what turned the short reservation into a stuck cursor; with the expansion in place that clamp is a no-op.
- **HTML export has two modes.** `export::html` produces a linked or self-contained file (base64 `data:` URIs for local images); the bundled stylesheet is `config/export/default.css`. `export::custom` shells out to a user-defined command (pandoc, weasyprint, …), hosting the intermediate HTML via `tempfile` and cleaning up on drop.
## Code Style

Write idiomatic, modern Rust; prefer language and standard-library features over manual workarounds.

- Prefer `#[derive(Default)]` over a hand-written `impl Default` when the output would be identical.
- Don't call `.into_iter()` on a value that already implements `Iterator`; call `.peekable()` etc. directly.
- Modern module layout: `src/foo.rs` alongside `src/foo/` — never `src/foo/mod.rs`.
- Prefer library helpers (`saturating_sub`, `unwrap_or_else`, …) over manual equivalents.

### Imports

Group with blank lines between: (1) `std`, (2) third-party crates (alphabetical), (3) `crate::` / `super::`.

```rust
use std::path::PathBuf;
use std::sync::mpsc;

use anyhow::Result;
use crossterm::event::{Event, KeyEventKind};
use ratatui::Terminal;

use crate::config::{Action, Config, KeyMap, Theme};
use crate::document::Buffer;
```

|---|---|---|

| Functions / methods | `snake_case` | `render_block`, `scroll_down` |
| Variables | `snake_case` | `file_path`, `col_count` |

### Formatting

4-space indentation; trailing commas in struct/enum literals and match arms; ~100-char target line length. Group methods with decorative section comments:

```rust
// ── Query ─────────────────────────────────────────────────────────────────

// ── Edit ──────────────────────────────────────────────────────────────────
```

### Types

- `enum` for domain state (`Mode`, `Action`, `Block`, `Inline`); `Option<T>` over nullable patterns.
- `#[derive(Debug, Clone, PartialEq, Eq, Hash)]` on core types.
- Lifetimes minimally and deliberately (e.g. `Renderer<'t>` borrows `Theme`).
- Newtype pattern for validated wrappers with `#[serde(transparent)]`.
- `StatefulWidget` for widgets that mutate scroll/cursor state; `Widget` for purely functional rendering.

### Error Handling

**Application code — `anyhow`:**

```rust
use anyhow::{Context, Result};

fn load(path: &Path) -> Result<String> {
    std::fs::read_to_string(path)
        .with_context(|| format!("Failed to read file: {}", path.display()))
}

// Non-fatal startup fallbacks:
let config = Config::load().unwrap_or_else(|e| {
    eprintln!("Warning: {e}. Using defaults.");
    Config::default()
});
```

**Library/domain errors — `thiserror`:**

```rust
#[derive(Debug, thiserror::Error)]
pub enum KeyMapError {
    #[error("unknown action name: '{0}'")]
    UnknownAction(String),
    #[error("unparseable key string: '{0}'")]
    UnparseableKey(String),
}
```

**Panic prevention:** `.saturating_sub()` instead of `-` on `usize`; `.min()` / `.max()` to clamp before indexing; bounds-check before any rope or buffer operation.

### Logging

Use `tracing` macros — **never** `println!` / `eprintln!`, which would corrupt the TUI. Logging is initialized only when `[dev] logging = true` (or `--log`), so tracing calls are no-ops in production.

**The subscriber's filter is a bare `debug`, and it has to stay unscoped.** `tracing_subscriber::fmt()` defaults to `info`, which silently dropped every `debug!` — the diagnostic trail the flag exists for (image decode, watcher events, link handling) is almost entirely at `debug`. The obvious repair, `edamame=debug`, is also wrong: `EnvFilter` matches on *target*, and the diagnostic call sites set their own (`image`, `watcher`, `link`, `mouse`, `app`), none under the crate's target path. Nothing in the dependency graph pulls `tracing` (`cargo tree -i tracing` lists only this crate and the subscriber), so an unscoped filter cannot be flooded by a chatty dependency. `RUST_LOG` overrides it. A new custom target needs no filter change; a new *dependency* emitting `tracing` means re-checking that claim.

### Tests

- Every source file gets a `#[cfg(test)] mod tests { ... }` block; integration tests in `tests/` import from the library crate (`edamame::`).
- `insta::assert_debug_snapshot!` for complex output (ASTs, rendered lines); `ratatui::backend::TestBackend` for widget rendering.
- `Box::leak(Box::new(Theme::default()))` for a `&'static Theme` in tests — intentional and safe there.
- Commit updated `.snap` files alongside the code changes that caused them.
